# blimp design (milestones 2–5)

SPEC.md says what blimp does. This file says how the pieces talk, so the server, the app UI and the app shell can be built separately and still fit.

## Repo layout

```
src/            blimpd (Bun + TypeScript, compiled to one binary)
test/           blimpd tests (bun test) + install test
app/            the Mac app (Tauri v2)
  src/          UI: React + TypeScript + Vite
  src-tauri/    native shell: Rust (SSH tunnel, store, notifications)
  e2e/          Playwright tests that drive the UI against a real blimpd over SSH
ios/            the iPhone app (SwiftUI; BlimpKit is its Foundation-only library, tested on Linux)
docs/           this file
install.sh      server setup
.github/workflows/  CI + release
```

Package manager everywhere: bun (`bun install`, `bun run`). No npm lockfiles.

## Connection

```
app UI ──fetch/WebSocket──▶ http://127.0.0.1:<local port>
                               │  ssh -T -L 127.0.0.1:<local port>:<home>/.blimp/blimpd.sock host 'cat >/dev/null'   (started by the Rust shell)
                               ▼
                        blimpd, listening on the unix socket ~/.blimp/blimpd.sock (mode 600, dir 700)
```

- The Rust shell runs the system `ssh` (`/usr/bin/ssh` on macOS, `ssh` on PATH elsewhere) with `-o BatchMode=yes`, so it uses the user's keys, agent and `~/.ssh/config` and never prompts.
- First it runs one command over SSH to learn the home folder and the token:
  `ssh -o BatchMode=yes [-p PORT] [USER@]HOST 'printf "%s\n" "$HOME"; cat "$HOME/.blimp/token"'`
- Both ssh calls also get `-o ConnectTimeout=10`, and `--` before the destination. A host or user that is empty, starts with `-`, or contains whitespace or control characters is refused before ssh runs.
- Then it starts the tunnel: `ssh -T -o BatchMode=yes -o ExitOnForwardFailure=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=3 -o ControlMaster=no -o ControlPath=none -L 127.0.0.1:<free port>:<home>/.blimp/blimpd.sock [-p PORT] [USER@]HOST 'cat >/dev/null'`, and waits (up to 10 s) until `GET /health` answers through it. No connection sharing: with `ControlMaster`/`ControlPersist` in `~/.ssh/config`, ssh would hand the forward to a shared master and exit, and the app could no longer close it.
- The tunnel's stdin is a pipe the app holds and never writes, and the remote command `cat >/dev/null` (instead of `-N`) runs until that pipe closes. However the app ends (quit, `kill`, force quit, crash), the OS closes the pipe, `cat` exits, and ssh ends once the webview's connections through it are gone. With `-N`, ssh outlived any exit that skipped the app's own cleanup.
- Both ssh commands get the app's PATH with `/opt/homebrew/bin` and `/usr/local/bin` added, so `ProxyCommand` and `Match exec` helpers from Homebrew are found when the app is opened from Finder.

### Token

The local port is reachable by anything on the Mac, including web pages, and WebSockets skip CORS. So every request carries a token.

- `blimpd serve` creates `<socket dir>/token` (32 random bytes, hex; mode 600) if it doesn't exist. The socket dir is `dirname(BLIMPD_SOCKET)`, default `~/.blimp`.
- HTTP: `Authorization: Bearer <token>`. WebSocket: `?token=<token>` (browsers can't set headers on a WebSocket).
- The phone has its own token: `<socket dir>/phone-token` (same format and mode), made by `blimpd pair`. blimpd accepts either file's token. It reads `phone-token` on every request, so deleting it (`blimpd pair --revoke`) refuses the phone at once, with no restart. WebSockets opened with the phone token are closed (code 4001) within a second once the file no longer holds that token. A missing or empty file matches nothing, so an empty token never gets in.
- Wrong or missing token → 401. Compare in constant time (both tokens are compared on every request).
- `blimpd pair [--url <url>]` (`src/pair.ts`) makes `phone-token` if it's missing or empty (the folder stays 700) and prints `blimp://pair?url=<percent-encoded url>&token=<phone token>`, as a QR code and as text. The URL is `--url` (http or https; trailing `/` dropped), else `https://<Self.DNSName without its trailing dot>` from `tailscale status --json`; with neither it exits 1 and says to install Tailscale or pass `--url`. Running it again shows the same token. The QR code is drawn with Unicode half blocks, two modules per character, with a 4-module border, in set colours (white on black) so it reads the same from a dark or a light terminal. The encoder is Nayuki's QR Code generator, vendored in `src/vendor/qrcodegen.ts` (no npm dependency). `blimpd pair --revoke` deletes `phone-token`; the Mac's `token` is untouched.
- CORS: every authorized response and the `OPTIONS` preflight have `Access-Control-Allow-Origin: *`. A 401 has none, so a web page can't read it to learn the port is blimp. `OPTIONS` returns 204 with `Access-Control-Allow-Headers: Authorization, Content-Type` and `Access-Control-Allow-Methods: GET, POST, PUT, OPTIONS`. (`*` is safe because the token is not a cookie.)

## blimpd API

All paths are absolute server paths. Errors are `{ "error": "<plain message>" }` with a 4xx/5xx status. JSON in, JSON out, except file bodies.

### Sessions

`GET /health` → `{ "version": "0.2.0", "home": "/home/u" }`

`GET /sessions` → `Session[]`, oldest first:

```ts
type Session = {
  name: string;          // zmx session name
  pid: number;
  clients: number;       // attached zmx clients
  created: number;       // unix seconds
  dir: string;           // real path Claude runs in
  cmd: string;
  kind: string;          // the kind it was started with (see Kinds); else claude if Claude's status file was found or cmd mentions claude, else shell
  label?: string;        // short label: for claude, its model's short name once known (see Jobs, context and work); for other kinds but shell, GLM, Codex, Codex sign-in, a custom kind's label
  sessionId?: string;    // Claude's conversation id
  transcript?: string;   // the conversation's file, once Claude has written one: another session can read it (Copy Reference)
  title: string;         // /rename title, else blimp's name (see Names), else AI title, else first prompt, else "(new session)"
  status: string;        // raw Claude status: busy | idle | waiting | shell | ""
  waitingFor?: string;   // raw Claude field
  updatedAt?: number;    // ms, last activity
  state: "working" | "waiting" | "done" | "unknown";
  stateSince?: number;   // ms
  prompt?: Prompt & { at: number };  // while waiting: what Claude asks, and when the wait started (see Chat)
  unread: boolean;       // Claude replied since either app last had it on screen (see Unread)
  note?: { status: "done" | "progress" | "question"; text: string; at: number };  // where it stands after its last turn (see Notes)
  jobs?: Job[];          // background work Claude started: commands, Monitors, agents, workflows (see Jobs, context and work)
  context?: { used: number; limit: number };  // how full Claude's context window is, in tokens
  model?: string;        // the model id of Claude's latest reply, from its transcript (see Jobs, context and work)
  git?: { cwd: string; branch?: string };     // the folder of the transcript's latest line, and the branch checked out there
  runnable?: string[];   // the commands in Claude's latest reply, newest first: what the Run button offers (see Runs)
  runnableAt?: number;   // ms, when that reply began: a run started before it is for an older reply
  run?: { command: string; parent: string; cwd: string; startedAt: number; endedAt?: number; exit?: number };  // on a run's own session (see Runs)
  handoff?: { state: "writing" | "started" | "failed"; child?: string; file?: string; error?: string };  // on a session that handed off (see Handoff)
  parent?: string;       // on the session a handoff started: the zmx name of the one it came from
  work?: Work;           // its checkout, branch and pull requests (see Jobs, context and work)
};
```

A field that has nothing to say is left out: a shell has no `jobs`, `context`, `model`, `git` or `work`.

`state` comes from whichever source is newer:
- Claude's status file (`statusUpdatedAt ?? updatedAt`): `waiting` or a non-empty `waitingFor` → waiting; `busy` or `shell` → working; `idle` → done.
- blimp's hook file `<socket dir>/status/<zmx name>.json` (`at`), so `~/.blimp/status/` by default and next to the temp socket for a test blimpd: see Hooks.
- Neither → `unknown`.

`POST /sessions` body `{ "dir": string, "name"?: string, "resume"?: string, "kind"?: string, "shell"?: boolean, "prompt"?: string, "model"?: string, "effort"?: string }` → 201 `{ "name": string }`.
`prompt` is Claude's first message (the phone's blank chat, or a message that resumes a past conversation): cleaned as chat `input` is, at most 100 000 characters, not empty, only for `claude` and `claude-glm`; it's passed as Claude's last arguments, `-- <prompt>`, so text starting with `-` isn't read as an option.
`model` (1 to 60 characters of `A-Z a-z 0-9 . _ - [ ]`, not starting with `-`) and `effort` (`low`, `medium`, `high`, `xhigh` or `max`) are passed as `--model <m>` and `--effort <e>` after `--mcp-config <file>`; launch flags beat Claude Code's settings. Anything else is 400 with a plain message. Only for `claude`: 400 "only Claude Code takes a model" (or "… an effort") for another kind, since GLM sets its own model and Codex and a shell have none. Not with `resume`: 400 "a resumed conversation keeps its model", since whether `--model` beats a resumed conversation's model wasn't checked. blimp never changes a running conversation's model. The apps send neither, so their sessions start on the user's default; `blimpd start` sends them (see Assistant).
`kind` is a kind's id (default `claude`; 400 for an unknown one or one that isn't available), or `codex-login` (Settings' Codex sign-in: `codex login --device-auth`, not listed in `/kinds`). `shell: true` means `kind: "shell"` (what older apps send). `resume` is a Claude conversation id (must match `/^[0-9a-f-]{36}$/`); the session runs `claude --resume <id>`; only `claude` and `claude-glm` take it. `dir` must be inside the home folder (see Files). The kind is remembered in `<socket dir>/session-kinds.json` (zmx name → kind; entries for sessions no longer listed are dropped at the next start) and reported as `Session.kind`.

### Kinds

`GET /kinds` → `[{ "id": string, "label": string, "available": boolean, "note"?: string }]`, in this order:

| id | label | available when | runs (`$SHELL -l -i -c <script> …`, arguments as `"$@"`) |
|---|---|---|---|
| `claude` | Claude Code | `claude` is found | `exec claude "$@"` |
| `claude-glm` | Claude Code on GLM | `~/.config/zai/key` isn't empty (and `claude` is found) | `export ANTHROPIC_BASE_URL=https://api.z.ai/api/anthropic ANTHROPIC_MODEL=… ANTHROPIC_DEFAULT_OPUS_MODEL=… ANTHROPIC_DEFAULT_SONNET_MODEL=… CLAUDE_CODE_SUBAGENT_MODEL=…` (GLM-5.3) `ANTHROPIC_DEFAULT_HAIKU_MODEL=…` (GLM-5.3-Flash) `API_TIMEOUT_MS=3000000; export ANTHROPIC_AUTH_TOKEN="$BLIMP_ZAI_TOKEN"; unset BLIMP_ZAI_TOKEN ANTHROPIC_API_KEY; exec claude "$@"` (models from `glm.model` / `glm.fast` in kinds.json if set, quoted). These are set in the script, after the login profile has run, so a profile's own Anthropic settings can't send the key elsewhere. The key is read from the file at start and comes in the environment as `BLIMP_ZAI_TOKEN`, never on a command line. |
| `codex` | Codex | `codex` is found | `exec codex "$@"` |
| custom | its label | its `command`'s first word is found | `exec "$@"` with its `command`, and its `env` added |
| `shell` | Shell | always | `$SHELL -l -i` |

"Found" means `command -v` finds it in the login shell, run as sessions run it (`$SHELL -l -i -c`, one shell for all names, cached 30 s), since nvm and `~/.local/bin` often join PATH only there (and Debian's `.bashrc` stops early in a shell that isn't interactive). A lookup that finds nothing (a profile that hung or failed) isn't cached, and `claude` is then started anyway, as before kinds. `note` says why one can't start ("Add a Z.ai key in Settings", "codex isn't installed") or, for Codex, "signed in" / "not signed in" (whether `${CODEX_HOME:-~/.codex}/auth.json` exists).

Custom kinds: `<socket dir>/kinds.json` = `{ "kinds": [{ "id", "label", "command": string[], "env"?: { [name]: string } }], "glm"?: { "model"?, "fast"? } }`. An id is `[A-Za-z0-9_-]{1,40}` and can't be a built-in one (`claude`, `claude-glm`, `codex`, `shell`, `codex-login`). A file that's there but wrong is ignored as a whole, and `/kinds` lists `{ "id": "kinds.json", "label": "Your kinds", "available": false, "note": "~/.blimp/kinds.json is ignored: <why>" }` where its kinds would be.

### Keys

`PUT /keys/zai` body `{ "key": string }` → 204. The key is 10–500 printable ASCII characters, no whitespace (else 400). It's written to `~/.config/zai/key` (folder 700, file 600) through a temp file and a rename. `DELETE /keys/zai` → 204, removes it. `GET /keys` → `{ "zai": boolean }`. No route returns a key.

### Secrets

A secret is a value (an API key, a password) given to a session's Claude without pasting it into the chat, where it would stay in the transcript (`src/secrets.ts`). `PUT /secrets/<NAME>` body `{ "value": string }` → 204. NAME is a letter, then up to 63 letters, digits or underscores (a shell variable's name); the value is 1–16 384 characters with no NUL (else 400). It's written to `<socket dir>/secrets/<NAME>` (`~/.blimp/secrets`, folder 700, file 600) through a temp file and a rename; a second PUT replaces it. `GET /secrets` → `[{ "name": string, "mtime": number /* ms */ }]` by name, never a value. `DELETE /secrets/<NAME>` → 204. `POST /secrets/<NAME>/tell` body `{ "session": string }` → 204 once typed: a paste plus Enter into that session (`typing.ts`) of "The secret NAME is saved in ~/.blimp/secrets/NAME (only you can read it). Read it from that file when you need it, for example `export NAME="$(cat ~/.blimp/secrets/NAME)" && your-command`, in the same command: a variable set in one command is gone in the next. Never print it, echo it, or put it in a file, a commit or a message." 404 for no such secret or session, 400 when Claude isn't running in it (no `sessionId`), 409 "Claude is asking something. Answer it first." The value is never typed, logged, put in argv or in the session list. The fs routes that read or write a file (`/fs/file`, `/fs/download`, `/fs/upload`, `/fs/create`, `/fs/mkdir`) refuse the secrets folder and everything in it, as they refuse blimp's key files (`files.ts` `guardFile`), for either token. The folder routes (`/fs/list`, `/fs/files`) refuse the secrets folder and any folder in it too (`guardList`), so they don't list the names. A folder that holds it (`~/.blimp`) still lists: `/fs/list` shows `secrets` among its entries, and `/fs/files` from it or a folder above it leaves out everything in the secrets folder, walked or from git. Both the Mac's and the phone's token may use these routes.

The sign-in tool is a separate program that types saved logins into pages. blimp knows two things about it. Its store folder, `~/.signin`, is guarded as blimp's key files are (`files.ts` `secretPaths`): no fs route reads, replaces, creates, renames, deletes or downloads it or anything in it, and the assistant's settings deny reading it. The folder routes can still list the names in it. A permission prompt for its tool, `mcp__signin__fill_login`, has the summary `Sign in to <site>` (`chat.ts` `toolSummary`; `site` is a saved login's name, cut to 80 characters, never a secret), so the phone and its notification say which site.

`DELETE /sessions/<name>` → 204: `zmx kill <name>`, then waits (up to 3 s) until zmx no longer lists it. 404 if there's no such session. Attached clients see close code 4000. Claude's conversation stays on disk, so it can be resumed.

`GET /folders/recent` → `[{ "dir": string, "lastUsed": number /* ms */ }]`, newest first, max 30, only folders that still exist. Source: each `<claude dir>/projects/*/` folder, its newest `*.jsonl`, the first `"cwd"` found in its first 50 lines. Not a folder in or under a temporary folder (`/tmp`, the system's temp folder): those are scratch, a test's or a helper agent's. Not a folder where only scripts ran Claude (`claude -p`, the SDK: the `"entrypoint"` beside that `"cwd"` starts with `sdk-`): `lastUsed` is the newest transcript a person started, so a script's run does not move a project up either. Not a hidden one (below), left out before the list is cut to 30. Plus the folders opened from the phone (`POST /folders/opened`), with `lastUsed` the later of the open and the newest transcript (in a temporary folder only the open counts, as its transcripts are left out); hidden and deleted ones are left out, and the list is cut to 30 after.

`GET /folders/hidden` → `string[]`: the projects you hid from the phone's strip, by folder (`src/hidden.ts`, `<socket dir>/hidden.json`, `{ "dirs": [...] }`, mode 600). `POST /folders/hidden` `{ "dir": string, "hidden": boolean }` → the list after hiding or showing it; 400 without a `dir` or a boolean `hidden`. `POST /sessions` in a hidden folder shows it again. The phone leaves a hidden project out of its strip even with sessions running there; the Mac's recent folders leave it out because `GET /folders/recent` does.

`POST /folders/opened` `{ "dir": string }` → `GET /folders/recent`'s list after it: the phone's folder browser opened `dir` as a project. 400 unless `dir` is a full path to a folder inside home. It shows the folder again if it was hidden, and keeps it in `<socket dir>/opened.json` (`src/opened.ts`, `{ "dirs": [{ "dir": string, "at": number /* ms */ }] }`, newest first, at most 30, mode 600), so the folder stays a project before Claude has run there.

`GET /conversations?dir=<dir>` → `[{ "sessionId": string, "title": string, "updatedAt": number /* ms, file mtime */, "unread": boolean }]`, newest first, max 50. The same list `/resume` shows in that folder: transcripts in `<claude dir>/projects/<dir with every non-alphanumeric char replaced by "-">/*.jsonl`.

`GET /conversations/<sessionId>/messages?dir=<dir>` → the last 200 chat messages of that past conversation (the chat's `history`, see Chat), read without starting Claude. 404 if `dir`'s transcript folder has no such conversation; `dir` must be inside the home folder.

### Accounts

When the Claude account in use runs out of usage, blimpd puts another saved login in place, tells the sessions that stopped on the limit to continue, and sends a phone notification (`src/accounts/`, design in `docs/superpowers/specs/2026-11-16-account-switching-design.md`). Every session shares one config folder, so every session is on one account at a time. A login is two things: `<claude dir>/.credentials.json` (600) and the `oauthAccount` object in `.claude.json`. A session picks up a new `.credentials.json` on its next turn, with no restart. Claude Code opens that file with `O_NOFOLLOW`, so it must stay a regular file. The file can hold other sign-ins too (`mcpOAuth`, for MCP servers). The account's own login is the `claudeAiOauth` key.

- **Off by default.** The switcher runs only when `config.json` has `"accounts": true` (`accountsOn`). It is checked every tick (1 s), so no restart. While it is off, blimpd files nothing and switches nothing. `blimpd accounts` says it is off and how to turn it on. On Linux, `blimpd account use` and `forget` work either way.
- **Linux only.** On a Mac, Claude Code keeps its login in the Keychain and reads `.credentials.json` only when the Keychain has none, so swapping that file switches nothing. There `accountsOn` is false whatever `config.json` says, and `blimpd accounts` prints only "account switching does not work on a Mac yet, because Claude Code keeps its login in the macOS Keychain". `account use` and `account forget`, given valid arguments, refuse with the same line (`blimpd: …` on stderr, exit 1).
- **Layout.** `<socket dir>/accounts/` (`~/.blimp/accounts`, folder 700) holds one folder per account, named by `accountUuid` (letters, digits and dashes, 1 to 64, else refused). Each has `credentials.json` (600, only `{ "claudeAiOauth": ... }`), `account.json` (the `oauthAccount` object, 600) and, once a different login has replaced it, `credentials.prev.json` (600, the account's login only: the one that was replaced, kept once, so a wrong save can be undone by hand by renaming it back). Beside them: `state.json` (600) with `active`, `order` (the order accounts were added), `out` (`{ <uuid>: { at, until } }`), `switchedAt`, `filed` (`{ mtime, at }`: the live file's mtime when blimp last settled who is in use, and when it did), `unknown` (`true` while blimp can't tell whose login is in place; a `state.json` without it is not) and `renewed` (`{ id, at }`: the last change filed as a renewal, below), and `log.jsonl` (600; past 1 MB it is renamed `log.1.jsonl`). Every file is written through a temp file and a rename. The folder is off limits twice: the file routes refuse it (`secretPaths`), and `/fs/list` and `/fs/files` leave out what is in it (`guardList`, as with `secrets`). Nothing here logs a token, and no error message carries one.
- **Filing rule.** Every tick (1 s) blimpd looks at the live file's mtime. First it checks whether the live login is exactly another saved account's (a swap whose note in `state.json` was lost): that account is taken as `active` and nothing is saved (log `adopted`). This check runs at once, and on the first tick after a start whatever the mtime. Any other change is filed once it is 30 seconds old (`SETTLE_MS`), because a `/login` writes its account record first, then its login file, and fires its notice last, after network calls that can take 20 seconds (a profile request with a 10-second timeout, tried twice; read from the Claude Code 2.1.325 binary). A switch waits while a change is still unfiled. Whose login it is:
  1. Claude Code fires its Notification hook with `notification_type: "auth_success"` when a `/login` succeeds. `blimpd hook` then writes `<socket dir>/auth-success.json` (`{ "at": <ms>, "dir": <the Claude folder as the hook sees it> }`, no secret), whatever the session. A session with another config folder (`CLAUDE_CONFIG_DIR`) runs the same hook, so blimpd ignores a note whose `dir`, as a real path, is not its own Claude folder's, and a note with no `dir`.
  2. If that note is newer than blimp's last settle (`filed.at`), the change is a `/login`. Its owner is the account `.claude.json`'s `oauthAccount` names, once that record's `profileFetchedAt` is newer than the settle too. Until then blimp waits. If the record has not followed within 60 seconds (`LOGIN_RECORD_MS`) of the change, nothing is saved and blimp can't tell whose login is in place (below). That happens when the profile request fails: the `/login` still succeeds and fires its notice, but the record has no `profileFetchedAt`.
  3. With no such note, it is a renewal: a session renewed the token, and it is saved under `active`. The record is not consulted. If no account is in use yet (a first run), the record names the owner, as a login. While blimp can't tell whose login is in place, the change is held instead (below).
  4. A change with nobody to file it under, or no login in it (after `/logout`), is noted as settled and logged `unfiled`. A save that fails for another reason is tried again on the next tick.
  A saved login is written only when it differs; the one it replaces is kept once as `credentials.prev.json`. A `/login` is saved under its account, which becomes `active`, and counts as a switch for the quiet time. Why the note and not the record: Claude Code rewrites `oauthAccount` by itself (about once a day at a process start, and in some cases at a token refresh), so a changed record does not mean a login. A saved login whose refresh token has expired can't be switched to; the next `/login` to that account replaces it.
- **Log in inside a session.** Claude Code fires a hook for a `/login` typed in a session. A login where it fires no hook (for example `claude auth login` in a plain shell) is taken for a renewal and saved under the account that was in use. To put that right, log in again with `/login` in a session: first to the account that was in use, then to the new one. Until the next save under that account, its own last login is still in its `credentials.prev.json`; its `credentials.json` holds the other account's. Don't use `/logout` on an account blimp keeps: it revokes the login on Anthropic's side (read from the 2.1.325 binary), so the saved copy stops working. Change accounts with `/login`, and drop one with `blimpd account forget`.
- **When blimp can't tell whose login is in place** (`state.unknown`). Set when a `/login` is given up after 60 seconds (rule 2): log `unknown` with `why: "login without a record"`. `active` is removed, and one phone notification goes out: title "blimp can't tell which account is logged in", body "The last /login was not saved. Run blimpd account use <email>, or /login again in a session." While it is set, a changed live login is filed only when its owner is certain: it equals a saved login (adopted), or a note newer than `filed.at` comes with a record fetched after it (a `/login`). Either one clears `unknown` and sets `active`. Anything else, a renewal or a first run's record, is held: noted as settled, saved under nobody, logged `held` once per change. Nothing switches: a limit stop marks no account out, no next account is picked, nobody gets `continue`. A stop from that time does not switch later either: the next limit stop does. `blimpd account use` clears it too, and puts its login in place without saving the one that was there.
- **A late notice.** A note newer than `filed.at` when there is no change left to file (the live mtime equals `filed.mtime`): a `/login`'s change may have been filed as a renewal before its notice came. So each renewal-filing notes `renewed` in `state.json`: the account it was saved under (`id`) and the live file's mtime for that change (`at`). The next renewal-filing replaces it; no login is in it. blimp never moves or restores a saved login by itself, so a late notice changes no file, `active` stays, and `unknown` is not set. The note is used up (`filed.at` is set to now) and `renewed` is removed. If the note is at or after `renewed.at` and less than 5 minutes after it (`LATE_NOTICE_MS`: a `/login`'s notice can't come later), one phone notification goes out: title "A /login may have been saved under the wrong account", body "Log in to <email> again with /login in a session." (the account `renewed` named, or its id). Otherwise nothing is told. The log gets `late login notice` with `account` (if `renewed` named one) and `told`.
- **`StopFailure`.** `install-hooks` adds the `StopFailure` hook to Claude's settings (Codex is untouched). `blimpd hook` writes the session's status file as a finished turn (`state: "done"`, `event: "StopFailure"`) plus `failure` (the hook's `error`, or `unknown`), `details` (`error_details`) and `message` (`last_assistant_message`), each cut to 300 characters. Only this event writes them. `rate_limit` and `billing_error` mean the account is out. The other errors change nothing here.
- **Which stops count** (`readStops`). Only a session of kind `claude`, not `claude-glm` (its limit is another provider's). Only a status file the session wrote itself: its `at` is not older than the session's start, and the session has a conversation id. A file left by an earlier session of the same name is ignored. A stop from before blimpd started is ignored. Each stop (a session and its `at`) asks for a switch once, and is logged once.
- **The switch.** (1) Mark the active account out: `at` now, `until` the reset time the stop's message names (`resetAt` in `rules.ts`), the latest one when several stops ask at once. When none names one (a `billing_error` never does), `until` is 5 hours later (`OUT_MS`). A time not after now, or more than 8 days on (`RESET_MAX_MS`: the longest limit window is a week), is taken as misread. The `switch` log line carries the time chosen as `outUntil`. A limit on one model (the Fable limit) marks the whole account out, although its other models still work; this is deliberate for now. (2) File the live file as above. If a change is still unfiled (under 30 seconds old, or a `/login` waiting for its record), the switch waits for the next tick. While blimp can't tell whose login is in place, there is no switch (above). (3) Pick the next saved account in the order added, after the active one, that is not out and whose login has not expired. If none, do not switch: one notification, "Every Claude account is out" ("Claude Code carries on by itself when a limit resets."). blimp does not check again on a timer. The next limit stop does, and Claude Code's own wait resumes a session when its limit resets. There is no automatic switch back. (4) Put the picked account's login in place: read `<claude dir>/.credentials.json`, replace only its `claudeAiOauth` key, keep every other key, write it through a temp file (600) and a rename, and set `active`. `.claude.json` is not touched. (5) A limit stop in the 30 seconds after a switch, or after a login by hand, does not start another one. It left before the swap.
- **Continue.** After a switch, blimpd waits 3 s (`CONTINUE_AFTER_MS`) and looks again. If the session list can't be read, it is tried 3 more times, 1 s apart; still unread, nobody is typed into and the notification says so. Every session still stopped on that same limit gets `continue` and Enter, typed as `typeInto` types. A session whose screen shows a list of choices or a confirm dialog (a cursor on a numbered row, "Enter to confirm", "Esc to cancel"), or whose screen can't be read (`zmx history`, 5 s at most), is left alone and counted. A session that moved on during the wait is not counted. With no switch in the tick, only a stop inside the 30 seconds after the last switch that is also under 60 seconds old (`RECENT_MS`) gets `continue`, so a restart does not type into an old stop. Each stop gets it at most once.
- **The notification.** To the phone only, through push, title "Now on <email>", body "<old email> ran out. 3 sessions continued." with " N left as they were." when some were left alone, "No session was waiting on it." when none, or "blimp could not read the sessions, so none was continued." An account with no saved email goes by its id. There is no Mac notification in this version.
- **Commands.** `blimpd accounts` prints each account's email (or id), "(in use)", "out until <time>", and when its login expires; never a token. While blimp can't tell which account is logged in, no account is "(in use)", and after the list it prints "blimp can't tell which account is logged in. Say which with: blimpd account use <email>, or log in again with /login in a session." `blimpd account use <email or id>` files the live login, puts that account's in place and sets `active`, with no `continue` and no phone notification; it prints `now on <email>`. It refuses a login that has expired, a change to the live file under 30 seconds old ("a login is still settling; try again in <n> seconds", n rounded up), and a `/login` still waiting for its record ("try again in a minute"). While blimp can't tell whose login is in place, it works and clears that; it first prints "the login that was in place was not saved, because blimp could not tell whose it was", and saves that login under nobody. `blimpd account forget <email or id>` removes the account's folder; it refuses the active one.
- **Connectors** (`src/accounts/connectors.ts`, design in `docs/superpowers/specs/2026-11-17-connector-gap-design.md`). claude.ai connectors (Slack, Gmail, Zapier and so on) belong to the Claude account, so a switch can leave sessions without one. blimp only reads: a reading is what `claude mcp list` prints about the account in use, run as a session's `claude` is (the login shell, `-l -i -c`), in the accounts folder (700, so nobody else can plant project config there) with stdin closed, killed after 60 s. Each line starting `claude.ai ` is a connector: its name up to the first `: `, its state `ok` (`Connected`), `signin` (`Needs authentication`) or `down` (anything else). After each loop tick a reading is due when there are two saved logins or more, the account in use is filed and known, the last switch is 30 s old, and its stored reading is missing, older than the switch, or a day old. It runs on its own, one at a time. A failed run (non-zero exit, a kill, no `Checking MCP server health` line) stores nothing, logs `connectors-failed`, and waits 10 minutes. A reading with no connector is stored only when another one 60 s to 10 minutes later says the same. A reading is thrown away if the account changed while it ran. It is kept in `<account>/connectors.json` (600): `{ at, connectors: [{ name, state }], told }`, names and states only. The gap is what is `ok` on another saved account's reading and missing here, and what needs a sign-in here and is `ok` on another. A new gap is told once (title "<email> is missing connectors", body "No A, B. C needs a sign-in. Add them at claude.ai/customize/connectors.") and logged `connector-gap`; `told` keeps it, so the same gap is not told again, an empty gap clears it, and a different one is told. A `tell` that throws leaves `told` as it was, so the next reading tries again. `blimpd accounts` prints the gap under each account that has one, from the stored readings: `  no A, B; C needs a sign-in`.
- **Log.** `log.jsonl` has one line per event, each with `at`: `stop` (session, `error`, `details`, `message`, `account`), `switch` (`from`, `to`, `outUntil` when a limit asked for it, `byHand` for `use`, written by the same writer the server uses), `login` and `renewal` (`account`), `adopted` (`account`), `unfiled` (a change with nobody to file it under, or no login in it), `unknown` (`why: "login without a record"`), `late login notice` (the `account` the renewal was saved under, if one was noted, and `told`), `held`, `not continued` (session, `error`) and `error` (a step that failed; the same text is written again only after 10 minutes). It holds ids, emails, times and the hook's own text, never anything from a credentials file.
- **What the account shown can get wrong.** A swap does not change `oauthAccount`, so `.claude.json` and what a session shows as its account can name the old account after a switch. blimpd does not write `.claude.json`, which every session rewrites. `state.json`'s `active` is the truth, and `blimpd accounts` says which account is in use.
- **Known since the first real limits** (spec finding 5, 2026-11-20). `StopFailure` sends `error: "rate_limit"`, and its message names the reset time in the server's own zone (an IANA name): "You've hit your Fable limit · resets Nov 25, 1pm (Europe/Berlin)", or with no date, the next time that clock comes round: "You've hit your weekly limit · resets 2pm (Europe/Berlin)". `resetAt` also reads a time with minutes ("2:30pm"), not yet seen. **Not known yet:** what the session shows at a limit. A limit can't be forced, so the log is there to answer it; until then a session that shows a menu is left alone.
- **Not in this version.** An accounts screen in the apps, a Mac notification, switching before the limit from the status line's `rate_limits`, and different accounts for different projects at the same time.

### Usage

Tokens, cost at API prices and limits, for every account and model on the server (`src/usage/`, design in `docs/superpowers/specs/2026-11-19-usage-design.md`). blimp only reads what Claude Code and Codex already write. The one change it makes to anyone's settings is the status line step, which the user runs and can undo.

- **Counting** (`scan.ts`). `blimpd usage-scan` is a child process blimpd runs (`service.ts`): 30 seconds after the start, then every 10 minutes, and on `GET /usage` when the last scan ended over a minute ago. One at a time. What a failed scan says goes to blimpd's own log. It reads every `*.jsonl` under `<claude dir>/projects` and `<codex home>/sessions` from where it last stopped to the last full line, in 8 MB chunks, and adds hourly totals to `<socket dir>/usage/usage.db` (`bun:sqlite`; folder 700, file 600, WAL). Each file's rows and how far it was read are saved in one transaction, so a scan stopped half way counts no line twice. A file that shrank is left alone; a file that is gone leaves the table, and its totals stay.
- **A Claude reply** is an `assistant` line with `message.usage` and a model other than `<synthetic>`. The same reply is written more than once, so `seen` keeps `message.id:requestId` for 40 days and a repeat counts nothing. **A Codex turn** is the growth of `total_token_usage` since the file's last `token_count`, under the model of the `turn_context` before it; cached input is taken out of input. The newest `rate_limits` is kept in `meta.codexLimit`.
- **Rows** are by UTC hour, account, model (as the vendor writes it), project (the line's `cwd`), helper or not (`isSidechain`, or a file in `subagents/`) and tier (`fast` from `usage.speed`; `long` when the model has a long-prompt price and the prompt is over its mark). The account is the one blimp's accounts log says was in use at that time (`whose.ts`: `switch`, `login`, `adopted`, `renewal`; `unknown` means nobody), or with no log the account `.claude.json` names. Other ids: `""` (before the log's first line, "Before account tracking"), `other` (a model that does not start with `claude-`) and `codex`.
- **How long.** On claude1 the first full scan took 189 seconds and counted 225,779 Claude replies. A second scan took 1.4 seconds.
- **The daily copy** (`dailyCopy` in `scan.ts`). After a scan has set `meta.scanEnded`, when `<socket dir>/usage/backups/usage-<YYYY-MM-DD>.db` (the UTC day) is not there yet, the scan writes it with `vacuum into` (a whole, consistent file; it can't run inside a transaction), folder 700, file 600. Then it deletes all but the newest 7 files there named `usage-<YYYY-MM-DD>.db`; other files stay. So there is one copy a day, made by the first scan of that day, and the last 7 days are kept. A copy that fails does not fail the scan: one line goes to stderr (`blimpd usage-scan: the daily copy failed: <why>`), which blimpd's log gets. To put one back: stop blimpd, copy `backups/usage-<day>.db` over `usage.db`, delete `usage.db-wal` and `usage.db-shm`, start blimpd. The next scan counts what is new since that copy's files table, so nothing is counted twice; replies in transcripts Claude Code has deleted since then are lost.
- **Cost** (`prices.ts`) is worked out when asked, never stored, so a corrected price corrects history. `PRICES` holds the vendors' prices on 2026-11-19, per million tokens; a date ending and `[1m]` are dropped before the lookup (`modelKey`). `<socket dir>/prices.json` adds or replaces prices; missing cache prices count as the input price, and a wrong file is ignored as a whole with a note, as `kinds.json` is. An entry there is matched by the id as written first, then by the shortened id (`entryFor`). GLM, Morph and Codex's `gpt-6-luna` have no price: they count in tokens, add nothing to cost and are listed in `unpriced`. Every place that shows a cost says "at API prices".
- **Limits** (`statusline.ts`). Claude's limit numbers reach only its status line command. `blimpd install-statusline` keeps the `statusLine` object in Claude's `settings.json` in `<socket dir>/usage/statusline.json` and points its `command` at `blimpd statusline` (other keys stay; `settings.json` is written as `install-hooks` writes it). It runs only from the built blimpd binary. `blimpd statusline` reads stdin, saves `rate_limits.five_hour` and `seven_day` to `<socket dir>/usage/limits/<account>.json` (temp file and rename, 600), then runs the user's own command with the same stdin and returns its exit code; whatever fails in blimp's part, that command still runs. The account is `state.json`'s `active`, or `one` with no accounts state. After a swap, nothing is saved for a session until the last 256 KB of its transcript holds a reply from the model (an assistant line with `message.usage`, model not `<synthetic>`, as the scan counts) dated after `switchedAt`: an API error line or a prompt after the swap is not one. Nothing is saved either while logins are saved but blimp can't tell which one is in place (`saveLimits`). `blimpd uninstall-statusline` puts the kept object back.
- **`GET /usage?days=&tz=`** (`summary.ts`, `summarize`): `days` 1 to 3660 (default 30), `tz` minutes east of UTC, −840 to 840; else 400. The last `days` local days, today included, never before the first reply. `{ scanning, firstDay, totals, days: [{ day, byAccount, byModel, tokensByAccount, tokensByModel }], accounts, models, projects, unpriced, note, previous, hours }`; `byAccount` and `byModel` are cost by id, `tokensByAccount` and `tokensByModel` all tokens by id (input, output, cache read and both cache writes; a model with no price is there too). A total is `{ replies, input, output, cacheRead, cacheWrite, cost, helperCost }`. `projects` is the 20 with the most cost, then one with `project: ""` for the rest. `previous` is the total of the same number of local days just before the range, cut at the first day; it is left out when the range starts at the first day (nothing before it). `hours` is there only for `days=1`: today's 24 local hours, `[{ hour (0 to 23), byAccount, byModel, tokensByAccount, tokensByModel }]`, by id as a day; an hour is floored by `tz` in minutes, as a day is, so a half-hour zone works. Before the first scan has ended, `scanning` is true and the rest is empty. A read-only open finds nothing until the first scan has made its tables, so it answers the same (`openUsage` in `db.ts`).
- **`GET /usage/now?tz=`** (`nowView`): `{ accounts: [{ id, email, inUse, at, fiveHour, sevenDay }], codex: { at, plan, windows: [{ minutes, used, resetsAt, reset }] }, today: { cost, tokens }, statusline }`. A window is `{ used (0 to 100), resetsAt (ms), reset }`; `reset` is true once its time has passed. With no saved account, the account `.claude.json` names, with the numbers saved under `one`. It does not start a scan.
- **`blimpd usage [--days N]`** (`cli.ts`) asks the running blimpd for both and prints the limits, the totals, and the top 10 by account, model and project. When the status line step is not in place it says how to put it in.
- No route returns a token, and nothing here reads a login.

### Unread

A conversation is unread when Claude wrote text (not only a tool call; not a side task's, not Claude Code's own `<synthetic>` note) after the newest reply that was on screen in either app. Read while the title is scanned (Sessions), as `replied`, the newest such entry's `timestamp`.
- `POST /seen` body `{ "sessionId": string }` → 204: the app has that conversation on screen; its replies up to now are seen. The apps send it while a session that shows `unread` is on screen (the phone: its chat open, the app in front; the Mac: the visible tab of a visible window). 400 for an id not matching `/^[0-9a-f-]{36}$/`; an id with no transcript changes nothing.
- **Where:** `<socket dir>/seen.json`, `{ "since": ms, "seen": { [sessionId]: ms } }`, mode 600, written through a temp file and a rename. blimpd makes it when it starts, if it's missing: `since` is then, so nothing from before counts as unread. Before it exists, nothing is unread.
- `unread` shows in `GET /sessions` (and so `/events`, within a second) and `GET /conversations`.

### Handoff

`POST /sessions/<name>/handoff` (no body) → 202 `{ "state": "writing" }`: Continue in New Session (src/handoff.ts). Claude Code sessions only (400 otherwise; 404 for no such session). blimpd types a request into the session (typing.ts, paste + Enter) to write `notes/<YYYY-MM-DD>/HANDOFF-<short-slug>.md` in its folder and reply with only its path. 409 while Claude asks something (the same text as the chat's refusal), while a handoff for it is being written, or before it has a transcript.
- Every second, blimpd follows the transcript from where it was when the request was typed. Once the request reached Claude (a `user` line, or a `queued_command` attachment while it worked), the first main-thread reply that names a `.md` file written since the request (absolute, or relative to the session's folder or the reply's `cwd`) is the handoff. A reply that is only a path may name any `.md` file. Inside a sentence, only a `HANDOFF*.md` path counts, and the last one named wins: while Claude works, its replies name the files it edits. A new session of the same kind starts in the same folder with first message `Read <file> and do it` (relative when inside the folder), as `POST /sessions` with `prompt` does. No file in 20 minutes: failed, "No handoff file came back".
- **Where:** `<socket dir>/handoffs.json`, `{ [parent zmx name]: { state: "writing"|"started"|"failed", child?, file?, error?, at, dir, kind, transcript, offset } }`, mode 600, through a temp file and a rename; only links with a live parent or child, from the last 7 days. A restarted blimpd goes on following a handoff being written.
- `GET /sessions` gives the parent `handoff: { state, child?, file?, error? }` and the child `parent: <zmx name>`.

### Runs

A run is a command Claude handed over, run when you click Run in an app, never before (`src/runs.ts`). The commands come from Claude's latest reply, since your last prompt (`src/runnable.ts`): a fenced block marked `bash`, `sh`, `shell`, `zsh` or `console` (the whole block; with `$ ` prompts, only the prompted lines), or inline code that starts with a command word (`bun test`) or with `! `. A bare `cd <dir>` isn't one. Newest first, at most 5, each at most 4000 characters. `GET /sessions` gives them as `runnable`, with `runnableAt`.

`POST /runs` body `{ "session": string, "command": string }` → 201 `{ "name": string }`. `session` is the Claude session the run is for. The command is 1–4000 characters, control characters out (else 400). 404 for no such session; 400 when Claude isn't running in it (no `sessionId`), since its result goes back there.
- The run is a zmx session of its own, of kind `run`, named `run-<HHMMSS>`. It starts in the folder of Claude's latest line (`git.cwd`, so a `cd` into a worktree counts) when that is still a folder in your home, else in the session's folder.
- It runs `$SHELL -l -i -c <wrapper> blimp <command> <runs folder> <shell>`. The wrapper gets the command as `"$1"` and runs it with `(eval "$1")` in a subshell: the command is an argument, never pasted into the script. An `exit` in it ends only the command. Ctrl-C stops the command, not the run.
- The wrapper prints `$ <command>`, then `── output ──`. When the command ends, it writes the exit code, prints `── exit N ──` and stays on as a login shell, so the output stays on screen until you close the session.
- **Where:** `<socket dir>/runs/` (folder 700). `<name>.json` is what blimpd started: `{ command, parent, dir, cwd, startedAt }`, mode 600, through a temp file and a rename. `<name>.end.json` is what the shell wrote when the command ended: `{ exit, endedAt }`, mode 600. The files of runs whose sessions are gone are removed when the next run starts.
- `GET /sessions` lists a run with kind `run`, label "Run", the command's first line as its title (70 characters), its Claude session's folder as `dir`, and `run: { command, parent, cwd, startedAt, endedAt?, exit? }`.

`POST /runs/<name>/send` (no body) → 204 once typed: Send result to Claude. blimpd types into the Claude session (`typing.ts`, a paste then Enter) ``[blimp run] `<command's first line>` finished with exit N.`` and the output's last lines in a fence. The output is what the run's screen and scrollback (`zmx history`) show between `── output ──` and `── exit N ──`: at most the last 40 lines and 4000 characters, colors out, and what looks like a secret taken out (activity.ts `redact`). 404 for no such run, or when its Claude session has ended; 400 while the command still runs; 409 while Claude asks something.

### Recap

The route returns a recap card ("where was I?"), which says what a Claude session is for, what's done, what Claude is in the middle of, what's stuck and on what, and what's next (`src/recaps.ts`). A small, fast model writes it, with the same call as names (`askClaude`, haiku on your own Claude sign-in).

`GET /sessions/<name>/recap?min=<n>` → `{ "goal": string, "done": string[], "doing": string[], "stuck": string[], "next": string[], "open": string[], "at": number /* ms */ }`. `open` is `doing`, `stuck` and `next` in one, for the apps from 0.3.0, which showed only Done and Open. A blimpd before 0.3.1 sends no `doing`, `stuck` or `next`. `min` (default 0) is the fewest prompts the conversation must have had; no app calls the route now (since 2026-10-23; the Mac's return card asked with `min=3`, and its right-click Recap without it).
- 400 when `min` isn't a whole number. 404 "no session named …"; 404 "Recaps are off" (`{ "names": false }` in `<socket dir>/config.json`, the names' switch); 404 "No conversation to recap" (not a Claude Code session, or no transcript yet); 404 "Not enough to recap yet" (fewer prompts than `min`, or no prompt or reply yet). A blimpd from before recaps answers the generic 404 "not found".
- 429 "Too many recaps this hour": at most 30 model calls an hour, across blimpd. 502 "Couldn't write a recap": the model's answer wasn't a card.
- **When it's written:** a recap is kept per conversation until Claude replies again. Until then the saved one comes back without a call. Two asks at once share one call.
- **What the model reads:** the title, the first request (when it isn't one of the latest), the last 3 requests and Claude's last 6 replies, each cut to ~300 characters. No tool calls or tool output.
- **The answer:** lines `GOAL | …` (exactly one), then `DONE | …` (what's finished), `DOING | …` (what Claude is in the middle of), `STUCK | …` (what's blocked, each saying on what, as "Waiting on you: approve the deploy") and `NEXT | …` (what's left after that), nothing else. Claude asking the user something, or waiting for a go-ahead, is STUCK ("Waiting on you: …"), never DOING; the prompt says so, as without it haiku put that under DOING. The first 4 DONE lines and the first 3 of each other kind are kept. The model leaves out a kind with nothing in it. An item that only says there is nothing ("Nothing left to do", "None", "No blockers") is skipped, as haiku still writes one at times; one that goes on to say what ("Nothing renders in Safari") is kept. Any other kind, `OPEN` too, means it isn't a card. Markdown marks are taken off; a line over 140 characters is cut at a word, with "…". It's shown as plain text.
- **The apps** don't show recaps (since 2026-10-23: nobody read them). The route stays, for later.
- **Where:** `<socket dir>/recaps.json`, `{ [sessionId]: { goal, done, doing, stuck, next, at, replies } }` (`replies`: how many replies the conversation had then), mode 600, through a temp file and a rename, the 200 newest kept. `open` isn't kept: it's made from the three. One kept by a blimpd before 0.3.1 (`{ goal, done, open, at, replies }`) isn't read, so it's written again the next time it's asked for.

### Jobs, context and work

What a Claude session is doing besides talking, read from its transcript (`src/activity.ts`). Like the titles, each transcript is read once, then only the lines added since. Only the main thread counts: a subagent's work is its own.
- **`jobs`:** background work Claude started: a Bash command run (or moved) in the background, a Monitor, an async agent, a workflow. `Job` = `{ id, kind: "bash" | "monitor" | "agent" | "workflow", label, startedAt, status: "running" | "done" | "failed" | "stopped", outputFile?, endedAt?, exit?, lastLine? }` (times in ms). A job ends with Claude Code's `<task-notification>`, with a TaskStop, or with the Claude process that started it: after a resume, what still ran from before has stopped. A finished job is shown for 30 minutes. `lastLine` is a running command's or Monitor's last output line, read from its output file's last 4 KB at most every 10 s. The label (120 characters) and the last line (160) have what looks like a secret taken out (`redact`).
- **`context`:** how full Claude's context window is. `used` is the latest reply's input tokens (input plus cache read plus cache write); after a compact, what the compact left. `limit`: 1 048 576 for GLM, 1M for an id with `[1m]`, 200k for Claude 3 and 4, else 1M (so a new model doesn't show fuller than it is).
- **`model`:** the model id of the latest reply (`message.model`, for example `claude-opus-5-5`), read with `context`; none before the first reply. A helper's replies are in its own transcript, so they don't change it. For kind `claude` it also sets `label`, the model's short name by what the id contains, ignoring case: `fable` → Fable, `opus` → Opus, `sonnet` → Sonnet, `haiku` → Haiku; else the id itself, cut to 24 characters, without a `[1m]` suffix. Other kinds keep their kind's label. The Mac app draws `label` on the row, the split header and the tooltip.
- **`git`:** `cwd` is the folder of the transcript's latest line, so it follows a `cd` into a worktree. `branch` is the branch checked out there, read from git's own files (the repo's `HEAD`, through a worktree's `.git` file), at most every 10 s per folder. Detached, not a repo, or gone: no branch.

`work` adds which checkout each Claude session is on, and its branch's pull requests (`src/work.ts`). `Work` = `{ branch?, root?, worktree?, prs?: [{ number, title, state, url }] }`. blimpd 0.3.0 also sent `clash`; the apps don't read it.
- **`root` and `worktree`:** from `git -c core.fsmonitor=false rev-parse --show-toplevel --git-dir --git-common-dir` in the `git.cwd` folder. `worktree` is true when its git folder isn't the repo's common one (a `git worktree add` checkout).
- **`prs`:** the branch's pull requests, the newest 3 in any state, from `gh pr list --head <branch> --state all --limit 3 --json number,title,state,url`. gh runs in the checkout through the login shell (`$SHELL -l -i -c`), so it finds gh and its sign-in as a terminal does; the folder and the branch go as `"$1"` and `"$2"`, never into the script. It is killed after 10 s. Only entries with an `http` or `https` link are kept, titles cut to 200 characters. Not looked up for `main` or `master`: a pull request's head is its own branch.
- **Caching:** git and gh run in the background, never while the session list is built (every second). The list shows what was last found: the root at most 60 s old, the pull requests at most 5 minutes old, per checkout and branch. One gh runs at a time. A gh that is missing or fails keeps what was found before. `blimpd sessions --json` waits for the roots and looks up no pull requests.

### Terminal

`GET /sessions/<name>/attach?token=…&cols=<n>&rows=<n>` upgrades to a WebSocket.

- 404 before upgrading if no zmx session has that name (`zmx attach` would otherwise create one).
- blimpd runs `zmx attach <name>` in a PTY (`Bun.spawn` with the `terminal` option) of `cols`×`rows`, env = blimpd's env minus `ZMX_SESSION`, plus `TERM=xterm-256color`, `COLORTERM=truecolor` (on macOS also `ZMX_DIR`: see zmx's socket folder).
- Server → client: binary frames, raw PTY output.
- Client → server: binary frames = keyboard input bytes; text frames = JSON control messages. Only one for now: `{ "type": "resize", "cols": n, "rows": n }`.
- When the socket closes, blimpd kills that zmx client (SIGTERM). The session keeps running.
- When the zmx client exits, blimpd checks whether the session still exists: if not, it closes with code 4000, reason `"ended"`; if it does (the user detached with ctrl+\), code 4001, reason `"detached"`.
- Backpressure: if the socket's buffered amount passes 8 MB (a stalled client), blimpd closes it with 1013 and kills that zmx client. The app reconnects and zmx redraws the current screen, so nothing is lost but scrollback the client never read.
- Several sockets on one session are fine: each gets its own zmx client. zmx keeps them in sync.

### Events

`GET /events?token=…` upgrades to a WebSocket. Server → client text frames:

- `{ "type": "sessions", "sessions": Session[] }`: sent on connect, then whenever the list changes. blimpd checks every 1 s. (A session that starts waiting must show in the app within 5 s.)
- `{ "type": "ports", "ports": Port[] }`: sent on connect, then when it changes (checked every 2 s). `Port` = `{ port, host: "127.0.0.1" | "::1", session, pid, command }`: a TCP port on loopback or any address that a program inside a blimp session listens on (`src/ports.ts`: the listening sockets, the process holding each, and whether it descends from a session's zmx daemon). On Linux the sockets come from `ss` (without `ss`, from `/proc`), and each process's parents from `/proc`. macOS has neither: the sockets come from `/usr/sbin/lsof -nP -iTCP -sTCP:LISTEN -F pctn`, which lists only your own processes, and every process's parent from one `/bin/ps -axo pid=,ppid=`. Each is killed after 3 s, and if either can't run, no ports are listed. `GET /ports` returns the same list.
- `{ "type": "browser", "tabs": BrowserTab[] }`: the server browser's tabs (see Server browser), sleeping ones too (`asleep: true`), sent on connect and when they change.
- `{ "type": "feed", "on": boolean, "unseen": number }`: the phone feed's switch and how many cards it hasn't seen (see Feed), sent on connect and when either changes.
- `{ "type": "assistant", "on": boolean }`: whether the assistant is on (see Assistant), sent on connect and within a second of a change (`PUT /assistant`, `blimpd assistant on | off`, or `config.json` edited by hand: blimpd checks every second).
- `{ "type": "fs", "paths": string[] }`: watched paths that changed (debounced 150 ms).

Client → server: `{ "type": "watch", "paths": string[] }` replaces this socket's watch set. Each path is watched non-recursively (a folder: its direct entries; a file: its content). The app sends the expanded folders of the tree plus the open files. Paths outside home are ignored. `{ "type": "active" }`: a blimp window is in front on the Mac (sent at most every 30 s), so the phone's notifications wait (see Push).

### Chat

For the phone: a Claude session as chat messages, and a way to type into it. Only for sessions where Claude Code runs (`sessionId` is known).

`GET /sessions/<name>/chat?token=…` upgrades to a WebSocket (404 for an unknown session). Server → client: `{ "type": "history", "messages": ChatMessage[] }` on connect (the last 200; the transcript is read from the start in 4 MB chunks, yielding between them, so a 100 MB one doesn't hold up other sockets), `{ "type": "append", "messages" }` as the transcript grows (checked every 250 ms; a tool message comes again with its output under the same `id`), `{ "type": "reset" }` then a new `history` when the conversation changes, `{ "type": "unreadable" }` when blimpd doesn't know the session's Claude `sessionId` (Codex, a shell) or the transcript can't be read. A new session has no transcript until its first message: it gets an empty `history`, then `append` once the file appears. So does a session whose Claude asks whether to trust its folder (no `sessionId` yet, see Folder trust below); once Claude starts, `reset` and its `history`. Close 4000 when the session ends, 1011 when blimpd can't read the session at all (zmx missing or refused) or can't read the transcript folder.

`ChatMessage` (`src/chat.ts`): `user` (typed prompts only: no tool results, meta entries, command wrappers, `!` commands or system reminders), `assistant` (text blocks; thinking is skipped), `compacted` (in place of the summary Claude Code writes as a prompt when it compacts; no text, the phone shows one "Session compacted" line, and an older phone, not knowing it, hides it), `shell` (a `!` command you ran: `input` is the command, `output` later what it printed, stdout then stderr; the phone shows the command as your bubble and the output under it, an older phone hides it), `tool` (`name`, a one-line `summary`, `input`, later `output` and `error`; input and output at most 20 000 characters, never cut inside a surrogate pair), `visual` (a page Claude showed; see Visuals), `file` (a photo or a video you sent, from `~/.blimp/uploads`: `file` its path, `name` its name, `image: true` for a picture Claude Code attached, `summary: "Sent <name>"`, `gone: true` once the file is no longer there; an older phone hides it). A `file` message comes from Claude Code's own note of where an attached picture came from (a meta entry `[Image: source: <path>]` after the prompt, so the card follows your words), or from a path in the uploads folder typed with your words (a video). In a `user` message the pictures' marks (`[Image #1]`, only when the prompt came with pictures) and those paths are left out; words that were only that make no `user` message.

Client → server: `{ "type": "input", "id", "text", "files"? }` (pasted as a bracketed paste, then Enter; `\r\n` and a lone `\r` become `\n`, then every control character except tab and newline is removed (U+0000–U+0008, U+000B–U+001F, U+007F–U+009F: ESC, ctrl+C, zmx's detach key ctrl+\\ …); at most 100 000 characters; refused with "Claude is asking something. Answer it first." while the session is waiting, because the Enter would confirm the prompt's highlighted choice; checked right before the paste, which is written together with its Enter, so a question can't start between them and leave the text in Claude's input box; Claude Code 2.1.300 takes a paste and Enter in one write as a sent message, or a queued one while it works; `files`: at most 10 paths of files in `~/.blimp/uploads` (anything else refuses the message, and nothing is typed), each typed first as a paste of its own, the path and a space, as the Mac's drop types one: Claude Code attaches a picture from a pasted path (`.png`, `.jpg`, `.jpeg`, `.gif`, `.webp`) a moment after the paste, and a message sent before that goes without it, so after a picture's paste blimpd waits until Claude Code's box shows a new `[Image #n]`, read off what its own zmx client is sent to draw, or 5 s, and checks again that Claude asks nothing; then the text and its Enter in one write, as without files; Claude Code 2.1.325), `{ "type": "answer", "id", "at", "pick", "label" }` (`at` = the prompt's `at`, when that wait started; `label` = the text of the choice the phone showed at `pick`: a permission's `options[pick]`, a question's `questions[0].options[pick].label`. Both are checked when its turn to be typed comes, because the options can change within one wait (the hook's Yes/No, then the screen's options, under the same `at`), and the same digit would press another choice. Presses the option's key, or replies "the question changed"; an answer without a `label` is refused the same way. `pick` answers only a permission or one single-choice question: the phone's voice answers use it), `{ "type": "answer", "id", "at", "answers", "labels" }` (every question of an AskUserQuestion dialog at once; see "Answering a question dialog" below), `{ "type": "interrupt", "id" }` (Esc: the phone's Stop), `{ "type": "interrupt", "id", "at" }` (the phone's Dismiss on a prompt: Esc only while Claude still waits on the prompt that started at `at`, else "the question changed", so a prompt answered on the Mac just before doesn't turn the Esc into a Stop), `{ "type": "deny", "id", "at", "text" }` (no, and why; `at` and `text` are required: Esc as Dismiss does, then, once Claude no longer waits (up to 5 s, else "Claude still asks something after Esc. Send your reason once it's answered."), `text` cleaned as `input`'s is, paste then Enter (checked again before the Enter); one write, so nothing is typed in between). Every message needs a string `id` of 1–100 characters; one without is ignored. Replies: `{ "type": "ack", "id" }` or `{ "type": "error", "id", "error" }`. All three return the error "open this session on the Mac" when blimpd doesn't know the session's Claude `sessionId`, except while Claude asks whether to trust its folder: then `answer` with `pick` answers that, and `input` is refused with "Claude is asking something. Answer it first." All three are de-duplicated by `id` (the last 100 per session): a repeat is acknowledged and not typed again. An `id` is remembered only after its write succeeded; a repeat that arrives on another socket while the first is still being typed waits for it and is acknowledged with it. Writes from one socket go one at a time, in order. When a socket closes, everything it was sent is still typed (the write in progress, the ones queued behind it, and a message still waiting for the history), so a Stop sent just before the phone's link drops still stops Claude; then its zmx client is stopped 100 ms later.

`POST /sessions/<name>/answer` does what the socket's `answer`, `interrupt` and `deny` do, without a socket (`src/answer.ts`, shared with it): the body is the answer's fields (`{ at, pick, label }` or `{ at, answers, labels }`), `{ "stop": true }` or `{ "stop": true, at }` for `interrupt`, or `{ "deny": true, at, text }`, each with an optional `id` (1–100 characters; de-duplicated with the socket's, so a retry with the same `id` is answered without typing again; without one, every request types). 200 `{ "id" }` once typed; 409 `{ "error" }` with the socket's reason when it wasn't (the question changed, stopped at the screen check, "open this session on the Mac" for a session without a Claude conversation unless it answers folder trust); 400 for a body that isn't one of these (no whole-number `pick`, no `answers` array, no `stop: true` or `deny: true`), or a deny without `at` or text; 404 for no such session. Its zmx client is started for the one answer, at the session's last size, and stopped after it.

While a socket has sent input, it keeps one zmx client attached for it, at the size the session was last shown at through blimpd (120×36 if never), and resized with it: a client of another size would resize the session for everyone. The client starts on the first write, after checking the session still exists (`zmx attach` would create a missing one; the reply is then "the session ended"), and is typed into once it is ready: on its first output (its own clear-screen after connecting; at most 1 s). If it ends on its own, the next write starts another. zmx 0.5 drops an ESC that is a new client's first input, so when a fresh client's first write starts with ESC and isn't the start of a bracketed paste (Stop, or Esc for No), blimpd first sends an empty bracketed paste, which zmx passes and Claude ignores.

`Prompt` (`src/prompt.ts`), from the hook's input: `permission` (`tool`, `summary`, `options`, `keys`; optional `input`: what it would run or touch, the Bash command, the file of Edit/MultiEdit/Write/Read/NotebookEdit, WebFetch's URL or WebSearch's query, other tools none (an MCP tool's JSON can hold a secret the redaction doesn't know), at most 2000 characters; `plan`: ExitPlanMode's plan, at most 8000; both with what looks like a secret taken out (activity.ts `redact`: `NAME=value`, `--token value`, Bearer/Basic, a URL's password, `name: value` headers and JSON fields whose name says key, token, secret, password or authorization, and a few known key prefixes), as is the Bash `summary`; `risky: true` when a Bash command pushes, deploys, forces, hard-resets, drops, deletes or is `rm -rf` (`riskyCommand`, words, not a parse)), `question` (AskUserQuestion's `questions`), `other` (Elicitation); and from the screen, `trust` (`folder`, `options`; see Folder trust). `Session.prompt` is present while both the derived state and blimp's hook file say waiting, and the hook's `at` is no earlier than the session's start. Claude Code 2.1.300 in default permission mode also sends a PermissionRequest for AskUserQuestion; blimpd treats it as the question, not a Yes/No, and as the same wait (it keeps the PreToolUse's `at`). Permission options vary by command and only the screen shows them, so blimpd reads them from `zmx history` once per wait (a screen without them is read again for 2 s after the hook: the hook can fire before Claude draws the dialog); without them they are Yes (`1`) and No (Esc). Whatever the hook file says, a `pick` answer to a permission or a question only ever types one digit 1–9 or Esc (for a question with previews, the digit then Enter; see "Answering a question dialog"). `answerable` is true for permissions, and for a question dialog blimpd can drive: 1–9 questions, each with 1–8 options (the "Type something" row, options + 1, must be one digit), no two with the same question text (the screen check below tells the steps apart by it).

#### Folder trust

In a folder it doesn't trust yet (nor any folder above it), Claude Code 2.1.300 asks before anything else (probed 2026-10-20):

```
 Accessing workspace:

 /tmp/blimptest-trustprobe-42dF

 Quick safety check: Is this a project you created or one you trust? (Like your own code, a well-known open source
 project, or work from your team). If not, take a moment to review what's in this folder first.
 …
 ❯ No, exit
   Yes, I trust this folder

 Enter to confirm · Esc to cancel
```

The rows aren't numbered; the cursor starts on "No, exit", ↓ / ↑ move it, Enter takes it (No ends Claude, and the session with it). No hook fires and Claude writes no status file until it's answered, so blimpd reads the screen instead: for a session started as Claude Code (its kind is `claude` or `claude-glm`, or its command mentions `claude`) with no `sessionId` yet, `zmx history`'s last 60 lines, at most once a second. When their end is that question (the folder under "Accessing workspace:", wrapped lines joined; the question; No then Yes; then only the footer), the session is `waiting` from its start (`stateSince` and the prompt's `at` are `created` × 1000) with `prompt: { "kind": "trust", "folder", "options": ["Yes, I trust this folder", "No, exit"], "answerable": true, "at" }`.

An `answer` with `pick` and `label` answers it (checked as for a permission): Yes is ↓ then Enter, No is Enter. Before each key blimpd waits up to 3 s for the screen to show the question with the cursor on No (before ↓ or No's Enter) or on Yes (before Yes's Enter); otherwise it stops there and replies "stopped: Claude's screen didn't show the folder trust question as expected. Finish it on the Mac." ↓ on a new zmx client comes after the empty paste (see above), which the question ignores.

#### Answering a question dialog

`answers` has one entry per question, in order: `{ "picks": [i, …] }` (option indexes), `{ "text": "…" }` (a typed answer, in place of "Type something"), or for a multi-choice question both. A single-choice question takes exactly one pick or one text; a multi-choice one at least one of either. `labels` has, per question, the labels of the picked options as the phone showed them, in the same order; with `at`, a dialog that isn't the one answered is refused with "the question changed". A typed answer is cleaned as `input` is, then made one line (runs of whitespace become one space); empty or over 2000 characters is refused.

What Claude Code 2.1.300 needs (probed with one attached client; the phone spec, docs/superpowers/specs/2026-10-19-phone-app-design.md, has what the probe saw): each question shows under a tab bar (`←  ☐ Color  ☒ Size  ✔ Submit  →`, or ` ☐ Drink` for one single-choice question) with numbered rows, then "Type something" (options + 1) and, after a line, "Chat about this". The cursor starts on row 1 of each question.
- single-choice pick k: the digit k+1 picks it and moves to the next question (one question: submits).
- single-choice text: the "Type something" digit puts the cursor on that row, a text field; the text as a bracketed paste; Enter takes it and moves on.
- single-choice with previews (any option has a `preview`; the hook's question then has `preview: true`): the previews are drawn in a box beside the rows, a long label wraps under its row, and there is no "Type something" row (probed 2026-10-21). The digit k+1 only moves the cursor there, from wherever it is; Enter takes it and moves on. blimpd types the digit with the question on screen and the cursor anywhere, then Enter once the cursor is on that row. A `pick` answer to one such question is typed the same way, with the same screen checks. A typed answer is refused: "this question takes one of its options; type an answer on the Mac".
- multi-choice: each pick's digit ticks its box without moving the cursor; ↓ × options to the text row and the text as a paste (pasting ticks it); ↓ to the "Next"/"Submit" row; Enter moves on. Without text, ↓ × (options + 1).
- after the last question, when there is more than one or it is multi-choice, a review screen ("Review your answers", `❯ 1. Submit answers`, `2. Cancel`): `1` submits.
- Esc cancels the whole dialog from anywhere ("User declined to answer questions"); blimpd never sends it in an answer.

blimpd builds those keys from the validated indexes only: digits, ↓ (`\x1b[B`), Enter and the paste of the cleaned text. Before each step it reads the screen (`zmx history`, the last 120 lines) and waits up to 3 s for the last tab bar to show that question's text with the cursor where the step expects it, exactly the expected boxes ticked, the typed text in its row, or the review screen. Otherwise it stops there, types nothing more, and replies "stopped: Claude's screen didn't show question N as expected. Finish it on the Mac." The tool's result in the transcript (the chat's tool output) lists the answers: `"Which color?"="Green", "Which size?"="Small"`; multi-choice answers are the labels and the typed text joined with ", ".

### Sending between sessions

`blimpd send <session> <message…>` (`src/send.ts`) types a message into another session's Claude, so sessions can read and message each other. The words after the name are the message (none: stdin). It reads the Mac's `token` next to the socket, checks `GET /sessions` (no such session, or one without a Claude `sessionId`: exit 1 with that), then sends the chat socket's `input` (see Chat) and waits for its ack. So the phone's rules hold: refused while Claude asks something ("Claude is asking something. Answer it first."), control characters taken out, a paste then Enter. Run inside a blimp session (`ZMX_SESSION`), the message starts with `[from blimp session <name>; reply with: blimpd send <name> "<message>"]` on its own line. Prints `sent to <session>` and exits 0 once typed; errors go to stderr as `blimpd send: <error>`, exit 1. No session uses it unless told to: the Mac's Copy Reference (a session's right-click) puts the command on the clipboard to paste into another session.

### Assistant

One Claude session, named `assistant`, that blimpd keeps running in `<socket dir>/assistant`, a folder that isn't a project (`src/assistant.ts`; design in `docs/superpowers/specs/2026-10-26-assistant-design.md`). Off unless `<socket dir>/config.json` has `"assistant": true`: `blimpd assistant on | off | status` sets it, and so does the Assistant switch in either app's Settings (`PUT /assistant`); `off` also ends the session; its folder and conversations stay.

- **Keep-alive:** every 5 s while it's on, if no session is named `assistant`, blimpd writes the folder's files and starts one: kind `claude`, the name exactly `assistant` (`startSession`'s `exact`), with `--permission-mode default` (the user's settings may run auto mode, which asks nothing), and `--continue` once Claude's projects folder for it has a transcript. Three starts within 2 minutes wait 10 minutes, logged.
- **Files:** `blimp.md` (what the assistant can do and its rules, naming this blimpd's own command) and `.claude/settings.json` are rewritten at every start; `CLAUDE.md` (`@blimp.md`, then the user's own) only when missing; `settings.local.json` never.
- **Settings:** `permissions.defaultMode: "default"`; `allow`: `blimpd overview`, `blimpd read`, `Read(~/**)`; `ask`: `blimpd start`, `send`, `answer`, and connectors' send tools (Gmail send, reply, forward; Slack send and schedule; Drive share; Zapier write actions); `deny`: reads of known secret files (`~/.ssh`, `~/.aws`, blimp's token, phone token, secrets, browser key and push key, the relay key `~/.blimp/relay-key`, the Z.ai key, Claude's and Codex's credentials, the sign-in tool's store `~/.signin`). Each command rule is there for `blimpd` and for the path blimpd runs from. `ask` beats any `allow`.
- **Look:** `blimpd overview` asks the running blimpd (`GET /sessions`, `/folders/recent`, `/folders/hidden`, `/conversations`) and prints every project but the hidden ones and the assistant's folder: each running session (not runs) with its state by the inbox's rules (`widgetState`: needs you, new reply, working; else idle or shell), how long, its label (a Claude Code session's model, else its kind's) and its note; what a waiting one asks, with options numbered from 1; and up to 5 unread past conversations per project (of the 10 newest projects) that no running session has open, with their ids. `blimpd read <session or conversation id> [--last N]` (20 by default, at most 200) reads the transcript here and prints `you:`, `claude:` (each cut at 2000 characters), `tool: <summary>` and `! <command>` lines.
- **Act:** `blimpd start <folder> [--model <m>] [--effort <e>] <message…>` is `POST /sessions { dir, prompt, model?, effort? }` (prints `started <name> in <dir>`). Only the words right after the folder are read as the two flags, in either order, each at most once; from the first other word on it's all message, so a message can say `--model`. A flag with no value, a value starting with `-`, or a flag twice is a usage error, and blimpd checks the values (see Sessions). The assistant's instructions say to start research and lookups with `--model haiku`, building from an agreed plan with `--model opus`, and to give no model for planning or when unsure, so the user's own default applies. `blimpd answer <session> <n>` reads the session's prompt from `GET /sessions` and posts `{ at, pick: n - 1, label }` to `/sessions/<name>/answer`, so it's refused if the question changed; it takes a permission, a folder trust question or one single-choice question, and sends the rest to the app. `blimpd send` is as above. All three print `blimpd <command>: <error>` and exit 1 on failure.
- **Jobs:** run by the assistant (`ZMX_SESSION` is `assistant`), `blimpd start`, `send` and `answer` take `--job <reason>` and then post `{ session, reason }` to `POST /assistant/jobs` (no `--job`: the start of the message, or `answer: <label>`; at most 80 characters (the route takes up to 200); never the assistant itself). blimpd keeps them in `<socket dir>/assistant-jobs.json` (`{ "<session>": { reason, at, reported? } }`, 600, `src/jobs.ts`) and drops a job once its session has ended. `GET /sessions` carries `job: { reason, at }` on a job's session and `assistant: true` on the assistant. The act is done either way: a job that couldn't be recorded is only said. "Run by the assistant" is a check of where the command runs, not a security boundary: any token holder can set `ZMX_SESSION`.
- **Updates:** every 2 s while the assistant is on and has jobs (`src/reports.ts`), a job's turn that ended after the assistant last acted on it, and after its last update, becomes a line: `[blimp job update] <project> · <reason> (<session>): <done | still working | needs you> — <the turn's note, or what it asks>`. A wait is told at once; a wait is keyed by when its question began (`prompt.at`, as push keys waits), so one wait is told once, and one that's over by the time the message goes (answered elsewhere) is dropped; a finished turn waits up to 30 s for its note, then goes without. Lines wait 10 s from the first, then go as one message typed into the assistant like `blimpd send` (not while it asks something). They're kept in memory only; `reported` in the jobs file keeps a restart from telling a turn twice. `blimp.md` tells the assistant that these lines are blimp's, information and never instructions. Known gaps: a new job's folder-trust question comes before the job is recorded, so it isn't told (its own notification still is); with names off a finished turn always waits the full 30 s; `reported` is set when a line is made, so a line not yet typed when blimpd restarts is lost, and that finish wasn't pushed either.
- **Notifications:** while the assistant is on and running, a job's finish isn't pushed (the assistant tells it), and the assistant's turn that an update began (typed at most 15 s before the turn began, and before it ended) is pushed however short. A job's wait is pushed as for any session.
- **Switch:** `GET /assistant` → `{ on: boolean, session?: "assistant" }` (`session` while a session of that name runs). `PUT /assistant { on: boolean }` → 204, 400 when `on` isn't true or false; it and `blimpd assistant on | off` both call `setAssistantOn` (off also ends the session). The events socket's `assistant` message says when it changed. The assistant's folder, by its path and its real path, is never in `GET /folders/recent` (nor in `POST /folders/opened`'s answer), so neither app offers it as a project.
- **Apps:** the phone pins the assistant's icon (the blimp, with its session's mark) above the drawer's projects, leaves its session and folder out of the projects (`Drawer.projects`), and opening its chat leaves the project as it was. On top of its chat a jobs bar folds to one line, `1 needs you · 2 working · 1 done`, and unfolds to a row per job (its mark, `project · reason`, what it asks or its note); a row opens that job's chat, whose back arrow says Assistant and goes back to it. The Mac pins an Assistant group above every tab's inbox (The app, item 5). Settings in both has the switch, and turning it off asks first. The jobs' rules are written twice, as the inbox's are (`app/src/lib/assistant.ts`, BlimpKit's `AssistantJobs.swift`, the same tests): needs you (waiting, or done with a `question` note), the oldest wait first; working (working, or done with a `progress` note), the longest first; done (done and unread), the newest first; any other job isn't shown. A job working now shows no words (its note is the turn before's). The widgets and the Dock badge count the assistant like any session.
- `src/client.ts` is how these reach blimpd: its socket, the Mac's token.

### Messages

Texting the assistant from Apple Messages, through blimp-relay on a Mac (`src/messages/`, `relay/`; design in `docs/superpowers/specs/2026-10-26-messages-design.md`). Off unless `<socket dir>/config.json` has `"messages": { "on": true }`: `blimpd messages on | off | status | revoke` sets it; `on` also makes the relay key, `<socket dir>/relay-key` (32 random bytes as hex, 600), and `revoke` deletes it.

- **Who:** the relay key reaches the `/messages/` routes and nothing else (anything else answers it 401), and no other key reaches them (401). While texting is off, each answers 403 `{ "error": "messages is off" }`. Every call counts as the relay calling.
- **`POST /messages/in { id, from, text, picture? }`** → `{ ok: true }`, or `{ ok: true, dup: true }` for an `id` taken in before (the last 500); 400 for a body that isn't a text. The text answers the question last texted, or is typed into the assistant once it isn't asking anything.
- **`GET /messages/out?wait=<s>`** → `{ texts: [{ id, text }] }`, held open up to `wait` seconds (at most 25) until there's one to send.
- **`POST /messages/out/<id>/sent`** → `{ ok: true }` removes that text from the outbox (`<socket dir>/messages.json`, 600).
- **Notifications:** while the relay has called in the last 5 minutes and no text has waited 5 minutes to go out, the assistant's own waits and finishes are texted, not pushed. Otherwise blimpd pushes once to say the relay is offline or can't send, and pushes those as before.

### Files

Every path must resolve, after following symlinks, to the home folder or something inside it. For a path that doesn't exist yet, its parent folder must. Otherwise 403. On a Mac, whose disk ignores letter case, the check for blimp's own files (`secretPaths`, `guardFile`, `guardEntry`, `guardList`, `listFiles`) ignores it too, so `~/.blimp/ACCOUNTS` is refused even before `~/.blimp/accounts` exists; on Linux it is another name.

`GET /fs/list?path=<dir>` → `{ "path": string, "entries": [{ "name": string, "kind": "file" | "dir", "size": number, "mtime": number /* ms */ }] }`, folders first, then by name. Symlinks are reported as what they point to; broken links are skipped.

`GET /fs/file?path=<file>` → the raw bytes. Headers: `Content-Type` from the extension (`application/octet-stream` if unknown), `X-Blimp-Mtime: <ms>`, plus CORS `Access-Control-Expose-Headers: X-Blimp-Mtime`. Over 50 MB → 413.

`PUT /fs/file?path=<file>&baseMtime=<ms>` body = raw bytes → `{ "mtime": number }`.
- If `baseMtime` is given and the file's mtime differs → 409 `{ "error": "changed on the server", "mtime": number }`. Without `baseMtime` it overwrites (the app's "keep mine" path).
- Writes go to a temp file in the same folder, then rename, keeping the original file's mode.

`POST /fs/mkdir` body `{ "path": string }` → 201 `{ "path": string }`: one new folder (not recursive). `POST /fs/create` body `{ "path": string }` → 201 `{ "path": string, "mtime": number }`: one new empty file. Both: 409 if the name exists, 403 if the parent isn't inside home or doesn't exist, or the path is one of blimp's own files or in the secrets folder (`guardFile`).

`POST /fs/rename` body `{ "from": string, "to": string }` → 200 `{ "path": to }`: a rename, or a move into another folder (the files pane's Rename and drag). `DELETE /fs/file?path=<file or folder>` → 204: a file, a link, or a folder with everything in it (`rm -r`; links inside are not followed). No trash: it can't be undone. Both act on the name itself (`guardEntry`): the path is its folder's real path with the name on, so a symlink is renamed or deleted as a link, never what it points to. Both refuse (403) a path outside home, home itself, blimp's own files, blimpd's socket (with it gone or moved, no new connection gets in until blimpd restarts), a folder that holds one (home, `~/.blimp`, `~/.config`), the secrets folder and anything in it, and a link to any of those. Rename: 409 if `to` is there (never over it; a case-only rename of the same file on a case-insensitive disk is allowed), 400 for a folder into itself or a folder inside it, 404 if `from` or `to`'s folder is missing (no folders are made), 400 across disks. A file moves by a hard link, which fails (409) if `to` was made meanwhile, as an upload's `new` does, then its old name is removed. A folder or a link is checked, then renamed: only an empty folder (or, for a link, a file) made at `to` between the two steps is replaced, and only your own programs could do that. Async on blimpd's thread.

`GET /fs/download?path=<file or folder>` → a file's bytes, streamed, any size (`Content-Disposition: attachment; filename*=UTF-8''<name>`); a folder as `<name>.tar.gz`, made on the fly by `tar -czf - -C <parent> -- <name>` (symlinks are stored as links, never followed). A cancelled request stops tar. A tar that couldn't read a file breaks the stream, so the app shows the download as failed and saves no archive with files missing (`tarFailed`): GNU tar's exit 2 (its 1, a file changed while read, is kept); on macOS any exit but 0, since a Mac's tar exits 1 for a file it couldn't read. On macOS it is `/usr/bin/tar` with `COPYFILE_DISABLE=1`, so it adds no `._` file beside a file that has extended attributes.

`POST /uploads?name=<name>` body = raw bytes, streamed → 201 `{ "path", "size" }` (`src/uploads.ts`): a photo or a video for a session, from the phone's chat. Saved in `~/.blimp/uploads` (made 700 if it isn't there; where the Mac's drop on a terminal puts its files too) under the name made one plain word (every run of characters outside `A-Za-z0-9._-` becomes `-`, leading dots and hyphens go, at most 120 characters), then `name-2`, `name-3` before its ending if a file has that name. At most 2 GB, as below. The path then goes with a message, in the chat socket's `files`; the phone reads a picture back with `GET /fs/file`. Files there over 30 days old are deleted when blimpd starts and once a day.

`PUT /fs/upload?path=<file>&mode=new|replace` body = raw bytes, streamed → 201 `{ "size", "mtime" }`. Written to a hidden temp file beside the target, then put in place: `new` with a hard link, which fails (409) if the name was taken meanwhile; `replace` with a rename over a file of that name. Never over a folder (409). At most 2 GB (413); 507 if `Content-Length` is more than the free disk space.

`GET /fs/files?root=<dir>` → `{ "files": string[] /* relative to root */, "truncated": boolean }` for ⌘P. Inside a git repo: `git ls-files --cached --others --exclude-standard`. Otherwise walk, skipping `.git`, `node_modules` and dot-folders. Either way, nothing in the secrets folder is listed (see Secrets). Max 20 000.

### Names

Claude writes its AI title once, from the first message, so it says how a session started, not what it does now. blimpd names Claude sessions itself (`src/names.ts`): every 5 s it looks at the running `claude` and `claude-glm` sessions and asks a small model for a name in 2 to 4 words.

- **When:** a session with at least one prompt and one reply, whose state is `done` or `waiting` (never mid-turn), and without a `/rename` title. A first name at once; a new one once 3 more prompts have come and the last name is 20 minutes old. One call at a time across blimpd, at most 30 an hour; a session whose call failed (or whose answer wasn't a name) waits 10 minutes.
- **The call:** `$SHELL -l -i -c 'echo blimp-name:; exec claude "$@"' claude -p --model haiku --no-session-persistence --strict-mcp-config --tools "" --max-turns 1 --settings '{"disableAllHooks":true}'`, so the login shell finds `claude` as it does for sessions; only what follows the `blimp-name:` line counts (a profile may print things). The conversation goes on stdin, which is then closed, never in the arguments (`ps` shows those). It runs in an empty private temp folder (no CLAUDE.md, removed after), without blimpd's `CLAUDE*` and `ZMX_SESSION` variables, and is killed after 60 s. No tools, MCPs or hooks, and nothing saved. It uses your own Claude sign-in (`--bare` would skip it), so a little of your Claude usage.
- **What the model reads:** the /rename or AI title if any, the first prompt, the last 3 prompts, and Claude's last reply, each cut to ~300 characters; no tool calls, tool output or system lines (read with `src/chat.ts`, only the lines added since the last check).
- **The answer:** one line, 1 to 6 words, at most 40 characters once quotes and trailing punctuation are off; anything else is ignored and the old title stays. It's shown as plain text.
- **Where:** `<socket dir>/names.json`, `{ [sessionId]: { name, at, prompts } }` (`at` in ms, `prompts` the prompt count then), written through a temp file and a rename, mode 600, the 500 newest kept. `GET /sessions` and `GET /conversations` show it after a /rename title and before the AI title.
- **Off:** `<socket dir>/config.json` = `{ "names": false }`. Read at every check, so it needs no restart. While it's off nothing is called, and titles are Claude's own again.

### Notes

For a project's inbox (below), blimpd notes where each Claude session stands after its last turn (`src/notes.ts`), with the same model call as names.

- **When:** every 5 s, a `claude` or `claude-glm` session whose state is `done` or `waiting`, with at least one prompt and one reply, and a prompt or a reply its last note didn't have. One call at a time, at most 120 an hour; a session whose call failed waits 10 minutes.
- **The call:** as for names (`askClaude`). The model reads the title, the last 3 prompts and Claude's last reply, each cut to ~300 characters.
- **The answer:** one line, `DONE | <words>` (did what was asked, waits for the next request), `PROGRESS | <words>` (not finished: stopped part way, or says what it does next) or `QUESTION | <words>` (asks you something or waits for a decision); the words at most 80 characters, trailing punctuation off but a question mark kept. Anything else is a failed try.
- **Where:** `<socket dir>/notes.json`, `{ [sessionId]: { status: "done" | "progress" | "question", text, at, turn } }` (`turn`: `"<prompts>/<replies>"` then), through a temp file and a rename, 600, the 500 newest kept. `GET /sessions` and `GET /conversations` carry `note: { status, text, at }`.
- **Off:** with names (`{ "names": false }`): nothing is called and no notes are sent.

### Inbox

A project's summary, the same in both apps (`app/src/lib/inbox.ts`, `ios/BlimpKit/Sources/BlimpKit/Inbox.swift`), from its running sessions and its Earlier conversations that no running session has open:

- **Waiting on you:** a session that waits, with what it asks (a permission's summary, a question's first question), else its note; or one that's done with a `question` note.
- **Done:** a session that's done and unread, with its note, unless the note says `progress`. Once it's seen (Unread), it leaves.
- An unread Earlier conversation goes under the heading its note gives, Done without one; a read one, or one whose note says `progress`, isn't listed.
- **Working:** a session working now, the longest-running first (by `stateSince`).
- **Other:** every other running session (a shell, a run, one read, one done with a `progress` note), newest first. The phone folds them as "+3 other"; the Mac's summary shows only Waiting on you and Done.
- **Needs you** (`needsYou`), in the shown project only: each of its running sessions that Waiting on you would list, and its unread Earlier conversations with a `question` note, the oldest wait first. Another project's waits are in its own inbox (the phone's banner and the top-left button's mark (☰ on the inbox, ‹ in a chat) and the project's icon in the drawer's strip still tell of them). The phone shows it on top of the inbox in place of Waiting on you, with the answers in the row (Allow and Deny over `POST /sessions/<name>/answer`, a single-choice question's options, or a button into the chat), once the real options are read (2.5 s at most after the hook, `PromptReady`).

Each line is the title, then its words; newest activity first within Waiting on you, Done and Other; an empty heading isn't shown. A line opens its session.

### Digests

A paragraph on where each project's work stands (`src/digests.ts`), with the same model call as names. No app shows it now (since 2026-10-23); blimpd still writes it and sends it with the session list.

- **When:** every 5 s, for each folder with `claude` or `claude-glm` sessions running, once what they are has changed since its last paragraph (a session started or ended, changed state or got a new note) and stayed so for 15 s. One call at a time, at most 60 an hour; a folder whose call failed waits 10 minutes.
- **What the model reads:** the folder's name, and each session numbered, with its title (~100 characters) and where it stands: waiting on the user (and its note), working now (and its latest request, ~200 characters), asking the user, stopped part way, finished (each with its note), or idle.
- **The answer:** one paragraph, 2 to 4 sentences, at most 600 characters, no lists or control characters. Each session it mentions is a link, `[a few words](n)`, n its number; a number it doesn't have, or a square bracket outside a link, is a failed try. A single line break is a space.
- **Where:** `<socket dir>/digests.json`, `{ [folder]: { text, sessions, at, key } }` (`sessions`: the names its links point at, link n at `sessions[n - 1]`; `key`: what it was written from), through a temp file and a rename, 600, the 200 newest kept. The events socket's `sessions` message carries `digests: { [folder]: { text, sessions, at } }` for the folders with sessions running; blimpd still sends it with the list, and no app shows it.
- **Off:** with names (`{ "names": false }`): nothing is called and no paragraphs are sent.

### Push

Notifications on Max's phone when a session waits on him or a Claude turn ends, with both apps closed (`src/push/`, design in `docs/superpowers/specs/2026-10-20-phone-push-design.md`). blimpd sends straight to Apple with Max's own push key: no relay.

- **Setup:** `blimpd push-key <file.p8> --key-id <id> --team-id <id>` copies the key from Apple's developer site to `<socket dir>/apns.p8` and the ids to `apns.json` (both 600). No file route serves the key. `blimpd push-test` sends "blimp can reach this phone" to every phone and prints Apple's answer for each. Without a key, blimpd sends nothing, and says so once in its log when a phone has asked for a push.
- **Phones:** `POST /push/device { "token": hex, "env": "development" | "production" }` → 204 adds one (`<socket dir>/push.json`, 600, at most 5, newest kept); `DELETE /push/device { "token" }` → 204 removes it; 400 for a token that isn't hex or another env. Apple's 410, `BadDeviceToken` or `Unregistered` removes a phone. `blimpd pair --revoke` removes them all.
- **When:** a watcher checks the session list every 1 s, always, once there's a key and a phone. A wait is told once it has lasted 3 s (a permission's options are read from the screen up to 2 s after it starts, and Yes and No need the final ones), once per `prompt.at` (or `stateSince` without a prompt). A Claude turn of 30 s or more is told when it ends (`working` to `done`; the turn's waits count). The list found first counts as seen, so a restart tells nothing again. While the Mac sent `active` in the last 2 minutes, a notification waits until 2 minutes after it, then goes only if the session still shows the same wait or the same finish. Codex and shell sessions: waits only.
- **What:** title "<session title> is waiting" or "… finished". A permission: its summary, category `permission` (the app's Yes and No), and `at`, `yes: { pick, label }` (the first option), `no: { pick, label }` (the last option whose label starts with "No", else the last). A plan and a risky command come without buttons (no category, no `at`, `yes`, `no`): a tap opens the chat, where the app's review and confirm apply. A question: its first question. Another wait: the folder's name. A finish: the last reply as plain text, 150 characters at most. Secrets come out of all text. `apns-collapse-id` and `thread-id` are the session's name, so a newer one replaces the older.
- **Sending:** one HTTP/2 connection per Apple service, kept while it works; a JWT (ES256, `iss` Team ID, `kid` Key ID) made again every 40 minutes; `apns-topic: dev.blimp.phone`. A failed send is logged with Apple's reason and not retried, except once on a fresh connection after a dropped one.

### Widgets

The iPhone's widgets (home screen and lock screen; design in `docs/superpowers/specs/2026-10-25-phone-widgets-design.md`) show every project's running sessions, the hidden projects' left out, by the rules the inbox gives each session: needs you (waiting, or done with a question in its note; the oldest wait first), new (done and unread, the note not "in progress"; the newest first) and working (the longest-running first).

- **`GET /widget`** → `{ at, counts: { needs, new, working }, rows: [{ session, dir, title, state, since }], lastFinished? }`, at most 9 rows (`src/widget.ts`). `since` is when it started waiting or working (ms).
- **The widget key** reads `GET /widget` and nothing else (anything else answers it 401), so the widgets can read while the phone is locked without the phone's token, which stays in the keychain until Face ID. It is HMAC-SHA256 of the phone's token with the text `blimp widget`, hex. The app gets it with `GET /widget/key` (phone token) → `{ key }`, 404 with no phone paired. To change the key: `blimpd pair --revoke`, then `blimpd pair` (a new phone token, and so a new key) and pair the phone again.
- **Widget push tokens:** `POST /push/widget { "token": hex, "env" }` → 204 and `DELETE /push/widget { "token" }` → 204, kept in push.json's `widgets` beside its `devices` (at most 5); 400 for a token that isn't hex or another env. `blimpd pair --revoke` removes them with the devices.
- **The pinger** (`src/push/widgets.ts`): every second, while there's a push key and a widget push token, the summary from the session list. When the counts, or the rows and their states, change, a widget push (`apns-push-type: widgets`, topic `dev.blimp.phone.push-type.widgets`, priority 5, `{"aps":{"content-changed":true}}`) tells iOS to reload the widgets, which then read `GET /widget`: a needs-you that wasn't there at once, anything else 2 minutes after the last ping at the earliest. A working row's time isn't a change. What it finds first counts as known. It shares the notifications' connection to Apple, and Apple's 410, `BadDeviceToken` or `Unregistered` removes a token. iOS decides when the widgets reload: expect minutes, not seconds.

### Visuals

A session can show you a page it wrote, a chart, a diagram, a small report or a 3D scene, on the phone and the Mac
(design in `docs/superpowers/specs/2026-10-26-visuals-design.md` and `2026-11-15-visuals-3d-design.md`).

- **The show tool** (`src/visuals/mcp.ts`): `blimpd visuals-mcp`, blimp's own MCP server over stdio, which every
  session blimp starts gets (see Server browser, Sessions). One tool, `show { path, title }`; Claude Code calls it
  `mcp__blimp__show`. Its description is Claude's instructions for a page. A call is `POST /visuals` on blimpd's
  socket with the Mac's token, for its session (`ZMX_SESSION`); the result is `Shown on the phone and the Mac.
  visual: <id>`, or `Not shown: <reason>` as the tool's error.
- **`POST /visuals { session, path, title }`** → 201 `{ id }` (`src/visuals/store.ts`): a copy as it is now, the
  folder `<socket dir>/visuals/<id>/` (700, its files 600) with `<id>.json` (`{ id, title, session, dir, source,
  at }`, 600) beside it. `path` is a page, copied as the folder's `index.html`, or a folder with its page as
  `index.html`, copied whole (names that start with a dot are left out). It is absolute or relative to the session's
  folder, under home and never one of blimp's own files (`guardFile`, for every file). The page: at most 2 MB of
  UTF-8. A folder: at most 100 MB and 500 files, no links, and no `kit` of its own at the top. A title of 1 to 80
  characters. 404 for no such file or session, 413 over a size, 400 otherwise. Copies over 30 days old are deleted
  when blimpd starts and once a day; over 2 GB in all, the oldest go first, then and after each show (never the one
  just made). A copy an earlier blimpd made is `<id>.html`, and is still read. Then it publishes
  `{ "type": "visual", id, title, session, dir, source, at }` on the events socket.
- **The visual key** reads `GET /visuals/<key>/<id>/` (the page; without the `/` too, for an app from before a
  visual could be a folder), `GET /visuals/<key>/<id>/<path>` (a file of the copy; 404 for a path that leaves it) and
  `GET /visuals/<key>/kit/<file>` (the kit), and nothing else. `GET /visuals/<key>/<id>/kit/<file>`, where a page's
  relative `kit/` paths land, is a 307 to the kit, so every visual shares one cached kit. The key is in the path, not
  a header, so the page's relative paths carry it, and a wrong one is a 401. It is HMAC-SHA256 of a token with the text `blimp visuals`, hex: the Mac's and the phone's each have one, from
  `GET /visuals/key` → `{ key }`, which each app asks for every time a page opens. A new phone token (`blimpd pair
  --revoke`, `blimpd pair`) changes the phone's.
- **The page's headers** (`src/visuals/http.ts`): `Content-Security-Policy: default-src 'none'; script-src
  'unsafe-inline' <own> <kit>; style-src 'self' 'unsafe-inline'; img-src data: blob: <own>; font-src data:;
  connect-src <own> blob:; frame-src 'none'; object-src 'none'; form-action 'none'; base-uri 'none'; sandbox
  allow-scripts`, nosniff, `Referrer-Policy: no-referrer`, cached 30 days (a copy never changes). `<own>` is the
  page's own folder, `http://<host>/visuals/<key>/<id>/` and the same with `https://`, and `<kit>` is
  `/visuals/<key>/kit/` written the same way, with `<host>` from the request's `Host` header: WebKit matches no source
  without a scheme under `sandbox`, and blimpd can't tell whether a proxy added TLS. So a page reads its own files
  and runs the kit's scripts and its own, and reaches no other visual, no other route and no website. (`blob:` is how
  three.js reads the textures inside a model.) A `Host` that isn't a plain host and port names nothing: the policy is
  then `script-src 'self' 'unsafe-inline'`, `img-src data: blob:` and `connect-src 'none'`, as before folders. A
  copy's files get the same policy, so an HTML file beside the page gets no more than the page. The kit's files: an
  hour, gzipped when asked. The kit's files, the redirect to them and a copy's files are sent with
  `Access-Control-Allow-Origin: *`: the page's origin is `null` (from `sandbox`), so its modules and requests are
  cross-origin, and the address holds the visual key, so only what already has the key can ask.
- **The kit** (`src/visuals/kit/`, built into the binary): `blimp.css` (blimp's colours for light and dark, the
  system font, `.grid`, `.card`, `.stats`/`.stat`, `.chart`, `.scroll`, tables, `.tag`), `blimp.js` (Chart.js's and
  Mermaid's look from it; it draws `<pre class="mermaid">` diagrams, draws both again when the scheme changes, and
  stops a tap on a link),
  Chart.js 4.5.1 and Mermaid 12.1.0, and three.js 0.187.0 as the ES modules it ships as (`three/three.module.js`,
  `three/three.core.js`, and under `three/addons/` OrbitControls, GLTFLoader with the two utils it imports,
  RoomEnvironment and RoundedBoxGeometry; a page maps `three` and `three/addons/` to them with an import map, as
  three.js's own examples do). All vendored (`kit/LICENSES.md`; `test/visuals-kit.test.ts` checks their sums).
- **In the chat** (`src/chat.ts`): a `mcp__blimp__show` call is a tool step (`Showing <title>`) until its result
  names the copy; then, under the same id, `{ role: "visual", title, visual: <id>, summary: "Showed <title>",
  gone? }`, `gone` when the copy is no longer kept. Older phone apps read the role as a tool step and hide it.
- **The Mac** (`app/src/lib/visuals.ts`, `app/src/components/VisualView.tsx`): a `visual` event for an open
  project's folder opens a `visual:<source>` tab after the galleries (one per file: showing it again moves the tab
  to the new copy), in front unless you're typing in a file, with the keyboard left where it was. The tab is an
  `<iframe sandbox="allow-scripts">` of the copy's URL.
- **The phone** (`ios/Blimp/Views/VisualView.swift`): a card in the chat (`VisualCard`), and full screen over
  everything a `WKWebView` that loads the page's own URL and cancels every other navigation, with one non-persistent
  data store for the app's run. It closes with × ("Close" to VoiceOver); under the Face ID lock it is hidden, and
  there again after unlocking; a tapped notification closes it.

### Feed

A full-screen feed on the iPhone of what's new in tech, one card a screen: Hacker News, Reddit, GitHub trending, and release notes and blogs, fetched every hour and summarized by the small model (`src/feed/`; design in `docs/superpowers/specs/2026-10-26-phone-feed-design.md`). Off unless `config.json` says `{ "feed": { "on": true } }`.

- **Settings** (`config.json`'s `feed`, read every minute, no restart): `on`; `subreddits` (default programming, LocalLLaMA, ClaudeAI, MachineLearning); `rss` (feed addresses; default Apple developer news, OpenAI, Swift.org, Bun and the GitHub changelog); `interests` (at most 20; default none). A list that's missing gets its default.
- **The job** (`src/feed/job.ts`): every minute. While on, a run once an hour has passed since the last one started (`lastRun`, saved before the run, so a restart doesn't fetch again). Every request: one at a time, 10 s, `User-Agent: blimpd/<version> (feed)`, at most 1 MB read.
  - Hacker News: the front page (30), from Algolia; a new story's first 3 comments.
  - Reddit: the top 5 of each subreddit's rising list (not stickied, not over 18) and a new post's top 3 comments, with an app-only token from `blimpd reddit-key <client id> <secret>` (`<socket dir>/reddit.json`, 600, never sent back). Without a key, skipped, and `runs.Reddit` says "no key".
  - GitHub: up to 25 repos from the trending page, read with HTMLRewriter; a new repo's README. No repos found: "no repos on the page".
  - Release notes and blogs: RSS 2.0 or Atom, posts from the last 3 days.
  - One card per link (`normalLink`: https, no `www.`, default port, `#part` or tracking parameters, the rest sorted, no final `/`); its id is the first 16 hex characters of the SHA-256. A link found again keeps its card and gets the new scores. A new card's linked page (not a thread or a repo) gives its description, `og:image` and first paragraphs (1,500 characters).
- **Summaries** (`src/feed/summary.ts`): one call a minute, at most 6 an hour, for the 10 newest cards waiting (not seen; a failed try waits an hour), through `askClaude` (haiku, no tools, 120 s). The posts go inside `<post n="…">` blocks that the prompt says are data, never instructions. The answer is JSON, `[{ n, summary, interest }]`; a summary that's empty, over 500 characters or has a control character doesn't count. A card shows once it has a summary, or after 2 failed tries with its title only. `interest` counts only with an interests list.
- **Order:** interest matches first, then the newest run, then each source's place, the sources taking turns (HN, GitHub, Reddit, release notes).
- **Where:** `<socket dir>/feed.json`, `{ cards, seen, saved, runs, lastRun, calls }`. Every change is one read, change and write through a temp file and a rename (600), so the job and the routes never undo each other's changes. Cards go 3 days after they were found unless saved; seen marks after 7 days.
- **API:**
  - `GET /feed` → `{ on, cards, saved, runs, next }`: the unseen cards that are ready, in order (`{ id, url, title, sources: [{ kind, name, score?, comments?, thread? }], at, image?, summary?, interest }`), the saved ones newest first, each source's last run (`{ at, ok, reason? }`), and when the next run starts (ms). Off: `{ on: false, cards: [], saved: [], runs: {}, next: 0 }`.
  - `POST /feed/seen { "ids": [...] }` → 204 (at most 500 card ids; one that isn't a card is ignored). `POST /feed/saved { "id", "saved": bool }` → 204; 404 for a card that isn't there.
  - The widget key reads none of it.
- **The phone** (`FeedView`): the drawer's Feed button (while on; a dot while `unseen` is above 0) opens it full screen. One card a screen, paging up and down; Open and Comments in Safari inside the app (http and https only; Comments asks which thread when a card has two); Save, and Saved from the top right. A card is seen once it has been on screen for 1 s and the screen moves on or the feed closes; seen ids go to `POST /feed/seen`, kept on the phone until they're sent.

### Hooks (status backup)

Claude's status files are internal and may change. So blimpd also installs Claude Code hooks that record status itself.

- `blimpd install-hooks` merges into `${CLAUDE_CONFIG_DIR:-~/.claude}/settings.json`, for each of `Notification`, `Stop`, `UserPromptSubmit`, `PostToolUse`, `PermissionRequest`, `PreToolUse` (with `"matcher": "AskUserQuestion"`), `Elicitation` and `StopFailure` (see Accounts): `{ "hooks": [{ "type": "command", "command": "'<absolute path of this blimpd>' hook", "timeout": 5 }] }`. It skips an event that already has a command containing `blimpd' hook` or `blimpd hook`. It keeps every other key and hook as they were, writes a one-time backup `settings.json.blimp-backup` before the first change, and writes atomically. Running it twice changes nothing. `install.sh` runs it.
- Codex: if `${CODEX_HOME:-~/.codex}` exists, the same install merges into its `hooks.json` (Codex reads hooks in Claude's format and sends the same JSON with `hook_event_name`), for `UserPromptSubmit`, `PreToolUse` (no matcher), `PostToolUse`, `PermissionRequest` and `Stop`: `'<blimpd>' hook codex`, same backup (`hooks.json.blimp-backup`) and rules. New entries go after the user's own in each event's list, because Codex keys each hook's trust by its place (`[hooks.state."<file>:<event>:<i>:<j>"]` in config.toml); Codex runs them only after the user trusts them in `/hooks`. `blimpd hook codex`: UserPromptSubmit, PreToolUse, PostToolUse → working; PermissionRequest → waiting; Stop → done. `notify` in config.toml is left alone. `blimpd uninstall-hooks` takes blimp's out of both files.
- `blimpd hook` reads the hook JSON on stdin. If `ZMX_SESSION` is set (Claude runs inside zmx, which sets it), it writes `<socket dir>/status/<ZMX_SESSION>.json` (the socket dir comes from `BLIMPD_SOCKET`, which Claude inherits from the session): `{ "state": "waiting" | "working" | "done", "at": <ms>, "since": <ms>, "sessionId": <session_id>, "event": <hook_event_name> }`. `at` is when it was last written (or, for a wait, when the wait started), and decides whether it or Claude's status file is newer; `since` is when the state began: a PostToolUse or UserPromptSubmit while already working keeps it, so `stateSince` counts the whole stretch. A file without `since` (an older blimpd) uses `at`. Notification with `notification_type` `permission_prompt`, `elicitation_dialog` or `elicitation_url_dialog` → waiting (other notifications, like `idle_prompt` about 60 s after a finished turn, are ignored); PermissionRequest, PreToolUse for AskUserQuestion, and Elicitation → waiting (these fire the moment the prompt appears; Notification can lag by seconds); UserPromptSubmit, PostToolUse → working; Stop → done; StopFailure → done, with the error (see Accounts). A Notification with `notification_type` `auth_success` (a `/login` succeeded) also writes `<socket dir>/auth-success.json`, `{ "at": <ms>, "dir": <claude dir> }`, whatever the session, and changes no status (see Accounts). A subagent's events come in the same session with its `agent_id`: a wait from one is recorded with `"agent"`, and a subagent's PostToolUse ends only its own wait, so a background agent working while Claude asks no longer turns the question into "working" (before, the phone showed the buttons for a second, then "Working…", and the question never came back). A question's PreToolUse names its `tool_use_id` (its PermissionRequest and Notification don't), kept as `"call"`: a main-thread PostToolUse with another `tool_use_id` doesn't end it either, as when Claude launches a background Agent and asks in the same message and the Agent call finishes after the question appeared (0.3.7 still had this). A permission's wait has no `call`, so any main-thread PostToolUse ends it, as before. A question left without its own PostToolUse (declined, and Claude goes on) gives way to Claude's status file, which is newer. Measured with a real Claude asking a question: the hook file said waiting 0 ms after the question appeared, and `GET /sessions` 12 ms after. It always exits 0 quickly and prints nothing.

### Service

`install.sh` runs blimpd as a user service, with no root.

- **Linux:** a systemd user unit, `blimpd.service`, with `Restart=on-failure`, `KillMode=process` (the sessions blimpd started keep running when it restarts) and `OOMPolicy=continue`. Without user systemd, the script prints a `nohup` command to start blimpd by hand.
- **macOS:** a LaunchAgent, `dev.blimp.blimpd`, in the desktop session (`gui/<uid>`): there the Keychain works, so gh and git can sign in. Its file is `~/Library/LaunchAgents/dev.blimp.blimpd.plist`:
  - `ProgramArguments` `[~/.local/bin/blimpd, serve]`, `RunAtLoad`, `ProcessType` `Interactive`.
  - `KeepAlive` `{ SuccessfulExit: false }` starts blimpd again after a crash, as `Restart=on-failure` does.
  - `AbandonProcessGroup` is `KillMode=process`: what blimpd started keeps running when blimpd restarts.
  - `EnvironmentVariables`: `PATH` (`~/.local/bin:/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin`; launchd's own is the last four), `ZMX_DIR` (`~/.zmx`) and `LANG` (`en_US.UTF-8`; launchd sets none).
  - stdout and stderr go to `~/Library/Logs/blimpd.log`.
- **Loading it:** `launchctl bootout` takes the old copy out, and the script waits (up to 10 s) until launchd no longer lists it, because `bootstrap` fails while it does. Then `launchctl enable` and `launchctl bootstrap gui/<uid> <the file>`. If nobody is logged in at the desktop (`launchctl print gui/<uid>` fails), the script only writes the file and says so: launchd loads it at the next desktop login.
- **Restart:** `launchctl kickstart -k gui/<uid>/dev.blimp.blimpd` (`scripts/install-here.sh` does this on a Mac, and `systemctl --user restart blimpd` on Linux).
- **Tools on macOS:** blimpd runs the system's `lsof`, `ps` and `tar` by full path (`/usr/sbin/lsof`, `/bin/ps`, `/usr/bin/tar`).
- **Checksums:** the script prints a file's SHA-256 with `sha256sum`, or `shasum -a 256` where there is none, and compares the text itself. It doesn't use `sha256sum -c`, which on macOS passes a damaged sum.

### zmx's socket folder

zmx keeps session sockets in `ZMX_DIR`, else `$XDG_RUNTIME_DIR/zmx`, else `${TMPDIR:-/tmp}/zmx-<uid>`. The last one is a predictable name in a shared folder, so blimpd creates it itself (mode 700) if it's missing, and refuses to start or run zmx if it isn't owned by the user or others can write it.

On macOS, with neither `ZMX_DIR` nor `XDG_RUNTIME_DIR` set, blimpd uses `~/.zmx` instead of the last one (`zmxDir`), with the same checks. zmx's own choice there is inside the per-user temp folder: its long path leaves about 46 bytes for a session's name, and macOS deletes old files there. On macOS blimpd also gives every zmx it runs `ZMX_DIR`, set to the folder it chose (`zmxEnv`), so zmx uses that folder and the sessions inherit it. The LaunchAgent sets `ZMX_DIR=~/.zmx` too. A terminal that runs `zmx` itself needs the same `ZMX_DIR` to see the sessions.

A session's name must fit in a socket's path: on macOS, zmx refuses a path (`<folder>/<name>`) over 103 bytes. So on macOS the folder part of a new session's name is cut until the whole name fits (`maxNameLength`, `newSessionName`; at least 1 character of it stays). The limit is 103, minus the folder's length, minus 1: 84 bytes for `/Users/mbeato/.zmx`. A name given exactly (the assistant's) isn't cut. On Linux, names are as they were.

### Performance

`GET /sessions` and the 1 s event check run often. Cache transcript titles per file and parse only bytes appended since the last read (keep the byte offset and the custom/ai/prompt state). Don't re-read whole transcripts every second.

### Starting sessions

`POST /sessions` creates the zmx session from inside a PTY of 120×36 (not with stdin at /dev/null), waits until that client has connected (its first output, zmx's clear) and the session is listed with a client (`clients>0`), then kills that zmx client. The list alone is not enough: zmx counts another `zmx list` that asks at the same moment as a client. A client killed before it sends its size loses the size, and zmx then never redraws for the first viewer, who gets an empty screen. Starts run one at a time, so two starts in the same second get different names. The session gets `TERM=xterm-256color` and `COLORTERM=truecolor`. The session then has a real size from the start: Claude renders its first screen properly, and output written before anyone attaches is shown to the first viewer.

### Server browser

One Chrome on the server that sessions drive through Google's Chrome DevTools MCP. Its tabs belong to folders. Spec: `docs/superpowers/specs/2026-10-20-server-browser-design.md`. Step 1 (this): sessions browse, and the app lists a folder's tabs.

**Chrome** (`src/browser/chrome.ts`):
- Which one: `google-chrome`, `google-chrome-stable`, `chromium` or `chromium-browser` on PATH. Then, on macOS, Google Chrome's app in `/Applications` or in `~/Applications`. Else the newest Playwright Chromium in `$PLAYWRIGHT_BROWSERS_PATH`, or without it in `~/.cache/ms-playwright` (on macOS in `~/Library/Caches/ms-playwright`, where it is the `chrome-mac-arm64` build, Google Chrome for Testing). `blimpd browser` prints which, or what to install.
- Started when first needed: a session's MCP connecting, `POST /browser/tabs`, a wake, or at blimpd start if a saved tab was used within the hour (see Sleeping tabs).
- Flags: `--headless=new --remote-debugging-pipe --password-store=basic --use-mock-keychain --no-first-run --force-device-scale-factor=2 --disable-blink-features=AutomationControlled`, `--user-agent` (normal Chrome's for its version, on Linux or on macOS as the server is, without "Headless"), and `--user-data-dir=~/.blimp/browser/profile` (700). There's no debugging port: only blimpd holds the pipe.
- `--force-device-scale-factor=2`: the screencast ignores the scale `Emulation.setDeviceMetricsOverride` sets, so without it a Retina Mac gets frames at half its pixels, and soft. A view at 1x gets them scaled down (`maxWidth`/`maxHeight`). Screenshots a session takes come at 2x too.
- Light while in use: from a scroll, click, drag or key (or pasted text) until 400 ms after the last, the view's screencast restarts at the page's size, a quarter of the pixels (Wikipedia: 400 KB a frame at 2x, about 150 KB at 1x), then at the screen's ratio again. Not "sharp once still": a blinking caret or a spinner never stops, so the page would flick between soft and sharp; this way only what you do makes it light.
- `--password-store=basic` is required. Without it, Chrome on a server with no desktop waits on a keyring for the cookie key, and every page load hangs. `--use-mock-keychain` is the same for macOS's Keychain.
- Not `--enable-automation`.
- A Chrome that exits as it starts is tried once more after 5 s. One started while the old blimpd's Chrome still holds the profile does that (code 21, at once); the old one quits within seconds of losing its pipe. Its first call answers "Chrome exited", which isn't ready.
- Chrome that exits later (a crash, or killed): its gate WebSockets close (1012), and it starts again with the saved tabs 5 s later. If it did that less than a minute before, the next need starts it instead, so a Chrome that keeps dying doesn't loop.

**Gate** (`src/browser/gate.ts`): blimpd's one pipe connection, shared by every client.
- Ids are rewritten per client.
- Flat sessions belong to the client that attached, and so do child sessions inside them.
- Discovery and auto-attach are the gate's own. A client sees only page targets of its folder: `targetCreated` for existing ones before the `setDiscoverTargets` reply, and attached before the `setAutoAttach` reply, as Chrome does.
- A target's folder is the creating client's, the opener's for a popup, or the one blimp opened it for. `openedBy` is the session.
- Any command with another folder's `targetId` is "No target with given id found".
- `Browser.close` is answered `{}` and does nothing. `Target.attachToBrowserTarget`, `Target.exposeDevToolsProtocol`, `Target.sendMessageToTarget`, `Browser.crash` and `Browser.crashGpuProcess` are refused.
- Every new tab opens in a window of its own (`newWindow: true`, added to every `Target.createTarget`): headless Chrome draws only each window's front tab, so a tab behind another would stop streaming to the app and to screenshots.
- blimpd's own attach (the live view) goes through the gate's line (`attachDirect`), so its `attachedToTarget` is never taken for a client's. A client that leaves before its attach comes back: the session is detached.
- When Chrome exits, every call waiting for it gets an error. The gate's WebSockets close (1012); the MCP doesn't reconnect, so a session's browser tools work again after the session restarts.
- Titles: Chrome doesn't announce a page's own title, so blimpd reads `Target.getTargets` every 2 s.

**Passkeys** (`src/browser/passkeys.ts`): a page that asks for a passkey gets Chrome's own passkey dialog, which headless Chrome never draws, and while it's open the page takes no clicks or keys (a Google sign-in's "Try another way" couldn't be clicked). Your phone's or Mac's passkeys can't reach the server's Chrome anyway (that needs Bluetooth near it).
- blimpd keeps a session of its own on every page target (`attachDirect`, from its `targetCreated`) with `WebAuthn.enable { enableUI: false }` and no virtual authenticators: the ask is never answered, no passkey is made or used, the page stays usable, and it hears `NotAllowedError` when its own timeout ends.
- Chrome turns that off for the whole tab whenever any session on it detaches (a view closing, an MCP quitting), so blimpd turns it on again from each other session's `detachedFromTarget`, sent at once so it reaches Chrome before anything sent after.
- It must be on before the ask: turning it on doesn't close a dialog already open.

**Listener** (`src/browser/service.ts`): `ws://127.0.0.1:<port>/s/<session>`.
- The port is the last one if it's free (so MCPs from before a restart still find it), written to `~/.blimp/browser/port`.
- Admitted only if all of these hold:
  - the connecting socket is blimpd's uid (`peer.ts`). On Linux, `/proc/net/tcp(6)` says so. macOS has no such table: there `/usr/sbin/lsof -nP -iTCP:<peer port> -sTCP:ESTABLISHED -F pun`, run as blimpd's user, lists that user's sockets only, and the one named exactly `<peer address>:<peer port>->127.0.0.1:<gate port>` must be among them, with blimpd's uid. lsof lists both ends of a local connection, and the other end is blimpd's own, so only that exact name counts. No such socket, an lsof that can't run, or no answer in 3 s: refused;
  - there's no `Origin` header (a web page's WebSocket sends one) and `Host` is `127.0.0.1:<port>` (no DNS rebinding);
  - `?key=` is the gate key: 32 random bytes as hex in `~/.blimp/browser/key` (600), made once. A page in the server's Chrome runs as you, so it passes the uid check, but it can't read the file. The key is in the MCP's arguments (it takes no other way), which only other users could read, and they fail the uid check;
  - the name is plain, and zmx has that session.
- On Linux the uid check comes first. On macOS it runs lsof, so it comes after the `Origin`, `Host` and key checks: a page, or a caller without the key, can't make blimpd start one.
- Its folder is the session's (real path).
- Tabs are saved to `~/.blimp/browser/tabs.json` (600) half a second after a change, and every minute while Chrome runs: `[{ folder, url, openedBy?, usedAt, madeAt }]` for an awake tab, `{ id, folder, url, title, openedBy?, madeAt, asleep: true }` for a sleeping one (times in ms), oldest `madeAt` first. Awake tabs are reopened when Chrome starts. Rows from before tabs slept have only `folder`, `url` and `openedBy`: they keep the file's order, and come back asleep.

**Sessions** (`src/browser/mcp.ts`, `src/kinds.ts`): sessions get blimp's MCP servers from two config files. `~/.blimp/mcp.json` has `blimp` only (`blimpd visuals-mcp`, the show tool; see Visuals); blimpd writes it when it starts. `~/.blimp/browser/mcp.json` has `blimp` and `blimp-browser` (`blimpd browser-mcp`); blimpd writes it once the gate listens. When the login shell finds `npx`, a Chrome is found and the gate is listening:
- Claude Code and Claude Code on GLM start with `--mcp-config ~/.blimp/browser/mcp.json`; otherwise with `--mcp-config ~/.blimp/mcp.json`.
- Codex always starts with `-c mcp_servers.blimp.command=… -c mcp_servers.blimp.args=[…] -c mcp_servers.blimp.env_vars=["ZMX_SESSION","BLIMPD_SOCKET"]`, and with the same for `mcp_servers.blimp-browser.*` after them when the browser is ready. `env_vars`: Codex gives an MCP server only a few variables of its own (`HOME`, `PATH`…) plus the ones named there, and blimp's servers need these two to find their session and blimpd.

`blimp-browser` runs `blimpd browser-mcp`. That reads `ZMX_SESSION` and the port file, then runs `npx -y chrome-devtools-mcp@1.11.0 --wsEndpoint ws://127.0.0.1:<port>/s/<session> --no-usage-statistics --no-performance-crux`. Your own MCP servers still load. Sessions already running get them when they're next started.

**Sleeping tabs** (`src/browser/service.ts`; spec: `docs/superpowers/specs/2026-11-23-sleeping-tabs-design.md`): a tab nobody has used for an hour (`SLEEP_AFTER`, no setting) sleeps: closed in Chrome, so it uses no memory, and kept in the list with the id it had, `asleep: true`.
- Used: made (also a wake, or a page a page opened), a session's `Target.getDevToolsTarget` for it (the MCP sends one before each tool call that acts on a page, and never by itself; no other command from a session counts), or a view of it opening or closing. A tab with a view open never sleeps. The gate keeps each tab's `usedAt` and `madeAt`; the apps don't get them.
- A timer checks every minute while Chrome runs. A tab is saved asleep before Chrome closes it.
- At a start (blimpd's, or Chrome's after it died), saved awake tabs not used within the hour come back asleep. Chrome starts with blimpd only if a tab is left to open.
- Wake (`POST /browser/tabs/<id>/wake`): the address opens again as a new tab, with a new id, in the same folder, with the same `openedBy` and `madeAt`, so it takes the old one's place in the list. Chrome starts if it isn't running. Two wakes of one tab at once give one tab. What was typed in the page and its scroll are gone; logins stay.
- To a session, a sleeping tab is closed: the MCP hears `targetDestroyed`. Sessions can't see or wake one. Sleeping tabs stay until closed.

**API**:
- `GET /browser/tabs?dir=` → `BrowserTab[]` = `[{ id, folder, url, title, openedBy?, asleep?: true }]` (all of them without `dir`), oldest first, sleeping ones too.
- `POST /browser/tabs { dir, url }` → 201 `{ id }`: http or https only, a folder inside home. 503 if there's no Chrome, with how to install one.
- `POST /browser/tabs/<id>/wake` → 200 `{ id }`, the woken tab's new id. 404 if `<id>` isn't a sleeping tab, 503 if Chrome can't start. The events socket's message with the new id can come before or after the answer.
- `DELETE /browser/tabs/<id>` → 204, or 404. A sleeping tab is removed from the list.

**Live view** (`src/browser/view.ts`): `GET /browser/tabs/<id>/view` (token, like every route; 404 for an unknown or sleeping tab) upgrades to a WebSocket.
- blimpd opens its own CDP session on the tab, straight on the pipe beside the gate.
- Server → app: binary messages, each a JPEG frame (`Page.startScreencast`, quality 70), just after `{ type: "frame", width, height }`, the page's size in CSS pixels to draw it at (a frame's pixels needn't be that times the screen's ratio: another Mac may have set the size, and Chrome draws at 2x whatever the emulated scale). Text: `{ type: "info", url, title, loading, canGoBack, canGoForward }` (on load, navigation and history changes); `{ type: "dialog", kind, message, defaultPrompt }` and `{ type: "dialog-closed" }`; `{ type: "copied", text }`.
- App → server: `{ type: "ack" }` after drawing a frame (Chrome keeps at most 3 frames unacked and each ack lets one more out, so a slow link gets fewer frames, not a queue); `{ type: "size", width, height, scale, mobile? }` (`Emulation.setDeviceMetricsOverride`, then the screencast restarts at that size times scale; `mobile: true` is the phone: mobile layout, touch emulation with 5 points, and Chrome on Android's user agent of the same version, which sites see from the next load); `{ type: "touch", event: "touchStart" | "touchMove" | "touchEnd" | "touchCancel", points: [{ x, y, id }] }` (`Input.dispatchTouchEvent`, the fingers down after the change; Chrome scrolls, glides, taps and zooms from them; after a `touchEnd`, blimpd answers `{ type: "focus", editable }`: whether a text input, textarea or contenteditable has focus, so the phone shows its keyboard); `mouse` (`Input.dispatchMouseEvent`), `key` (`Input.dispatchKeyEvent`), `text` (`Input.insertText`); `{ type: "go", url }` (http or https only); `{ type: "nav", action: "back" | "forward" | "reload" }` (back and forward through the tab's own history); `{ type: "copy" }` (the selection: in the focused text field, else the page's; asked after each click, key, paste and page load, and kept selected in the app's hidden typing field, so the Mac's Copy and Cut, from the Edit menu or ⌘C/⌘X, copy it at once: a copy that waited for the server would be too late for the Mac to write the clipboard. Cut then sends Ctrl+X to the page); `{ type: "dialog", accept, text? }`.
- Several views of one tab (two Macs, a Mac and the phone) all get frames. The one used last sets the page's size and mode: a size, or input that's more than a pointer passing over, makes it the owner, and the last owner's settings come off first (input waits for that, so it lands on the page laid out for its screen). Chrome drops a CDP session's size when the session leaves, so when the owner closes, the newest view left with a size puts its own back on: the Mac's desktop layout returns when the phone leaves. A closed tab closes its views ("Tab closed").

## The app

### Rust shell (`app/src-tauri`)

Commands for the UI (`invoke`):

- `connect({ host: string, user?: string, port?: number, attempt?: string }) → { id: string, port: number, token: string, home: string }`. `id` is `user@host:port`. Reuses a live tunnel for the same id. Errors are plain sentences (for example "SSH to claude1 failed: Permission denied (publickey)"). `attempt` is Add server's token for one try (see Add server); a server's link passes none.
- `disconnect({ id: string, attempt?: string })`: stops that server's tunnel and any connect still starting one. With `attempt` it stops only the connect with that token instead and leaves every tunnel alone: Rust keeps the token as cancelled (also when the cancel arrives before its connect does; at most 32 such early cancels, the oldest forgotten first, and a token goes when its connect ends) and checks it when the connect starts, after the info ssh and before the tunnel's ssh is spawned, while it waits for `/health`, and under the lock that puts the tunnel in the map. A cancelled try ends with "Connecting to <host> was cancelled." and leaves no tunnel and no ssh (the info ssh, if running, ends by itself). Tokens longer than 64 characters are refused (`Tries` in `src/tunnel.rs`, unit tested).
- `drop_tunnel({ id: string, port: number })`: stops that server's tunnel only if it is still the one on `port`, leaving port forwards and a newer tunnel alone, and without `tunnel-closed`.
- Event `tunnel-closed` with `{ id }` when an ssh child exits. The UI reconnects with backoff (1, 2, 5, 10 s, then every 10 s). Every window's links share the one tunnel per server.
- Wake: ssh notices a connection that died while the Mac slept or changed networks only after up to a minute (ServerAlive 15 s × 3), and `connect` reuses it meanwhile. So each window watches for a gap of over 7 s between its 2 s timer ticks (the Mac slept) and for the `online` event. Then each link (unless the browser says it is offline) asks `/health` through its tunnel; with no answer in 8 s it calls `drop_tunnel` and connects again. An offline link also retries at once instead of waiting out its backoff.
- Updates: the `updater` plugin checks `https://github.com/mbeato/blimp/releases/latest/download/latest.json` (made by the release workflow, `scripts/latest-json.ts`) at launch and every 6 h, and on blimp > Check for Updates… (the menu's `check-updates` item; see macOS menu); it takes only bundles signed with the key whose public half is `plugins.updater.pubkey`, then `relaunch` (`src/relaunch.rs`) quits and a small helper opens the app again once this copy is gone (Tauri's own restart opens a second copy with `open -n` while the first is still running, and the Dock gives it an icon apart from the one kept in the Dock). `update_server({ server }) → lastLines` runs `curl -fsSL https://github.com/mbeato/blimp/releases/latest/download/install.sh | sh` on the server over ssh (refused in a debug build pointed at a test blimpd); the UI offers it when blimpd's `/health` version is older than the app's. That ssh (also Install blimpd's) has `-o ServerAliveInterval=15 -o ServerAliveCountMax=3` besides BatchMode and ConnectTimeout, so a server that stops answering mid-install ends it within about a minute instead of never.
- Servers not yet added (`src/tunnel.rs`): `ssh_hosts() → string[]`: the `Host` names in the Mac's `~/.ssh/config` that are not patterns (no `*`, `?` or `!`), each once, at most 200, for Add server's suggestions. It reads that one file and returns only the names; a missing or unreadable file gives none. `install_server({ host, user?, port? }) → lastLines`: the same install script as `update_server`, for a server that has no tunnel yet (blimpd isn't set up there). It takes only host, user and port, checked as `connect` checks them, and it is refused in a debug build pointed at a test blimpd, as the update is. `connect`'s error for a server with no blimpd token starts "blimpd isn't set up on <host>"; the UI knows it by those words (`isNotSetUp`), and a Rust test pins them.
- Menu (`src/menu.rs`): `set_menu({ spec })`: the page's description of the macOS menu bar, checked and drawn by Rust. A click sends the focused window the event `menu` with the item's id. See macOS menu.
- Port forwards (`src/tunnel.rs`): `forward_port({ server, host, port }) → localPort`: one more ssh (`-L 127.0.0.1:<free>:<host>:<port>`, host 127.0.0.1 or ::1 only), reused while it runs, closed by `unforward_port({ server, port })`, with its tunnel, or when the app exits.
- The shell has no browser of its own: browser tabs are the server's Chrome, drawn in the page (see Server browser). The shell finds windows with `get_window`/`windows()` and its commands take a `Window` (Tauri's `unstable` feature).
- Transfers (`src/transfer.rs`): `download({ server, path, id }) → savedPath` streams `/fs/download` to `~/Downloads` under a free name (`name 2.ext`…). `upload({ server, local, remoteDir, name, mode, id }) → files` streams a file, or a folder's files and folders, with `/fs/upload` and `/fs/mkdir`; it reads only paths dropped on a window (Tauri's drag-drop event) or picked in `pick_upload()` (the system file picker), and what's inside them. The page names the server by tunnel id; port and token come from the live tunnel. Progress: `transfer` events `{ id, done, total }`; `cancel_transfer({ id })`.
- Windows (`src/windows.rs`): `open_window({ init })` opens a new window `w-<n>` that starts from `init` (a query string: a place, `server`, `dir`, `session`, or a whole `layout`), handed to the page as `window.__blimpInit` (JSON-encoded, never pasted into script). `focus_project({ project, init }) → bool` brings forward another window with `project` (`"<server key>\n<folder>"`) in a tab and sends it `select-session`. `set_window_projects({ projects })`: every tab's folder. `drop_session({ init, x, y }) → bool`: a session let go outside this window, at a point on screen; the window under it gets `drop-session`, else a new window opens there. `drag_hover({ init, label, x, y }) → bool`: while such a drag is outside its window, the window under the point gets `drag-hover` `{ init, label, x, y }` (the point in its page) and the one it left gets `drag-hover` null; `init` null ends it (so does `drop_session`). `set_shown({ sessions }) → map`: every split in every tab, broadcast as `shown`, so other windows mark those sessions; `focus_session({ session, init }) → bool`; `take_session({ session })` sends `release-session` to windows that show it. A closing window makes the most recently focused one left save its tabs (`remember-layout`). `set_viewing({ sessions })`: the sessions on screen while that window has focus. `claim_notice({ session, key }) → bool`: false if a focused window shows `session` or another window already claimed `key` (`<server>/<session>/<wait start>`), so one wait gives one notification across windows. Clicking the Dock icon with no window open opens one.

All ssh children are killed when the app exits normally; on any other exit they end by themselves (see Connection). Plugins: `notification`, `store` (server list in `servers.json`, recent projects per server and the last server in `recent.json`), `opener` (links, http and https only). macOS: a menu bar the page describes (see macOS menu). Window 1400×900, min 900×600, title "blimp". Bundle id `dev.blimp.app`.

A model with no price says "no price" in `--fg-faint`, with an empty bar and "—" for its share. Under the model table: `note` when `prices.json` was ignored, and "No price for: …. Add them to ~/.blimp/prices.json on the server." when `unpriced` has names.

While `scanning`: "Counting your history…", asked again every 5 s. A 404 says blimpd there is too old to count usage and to update it; any other error shows as other dialogs show theirs.
- **The chart** (`CostChart`; `chart`, `axis` and `busiest` in `lib/usage.ts`): drawn by hand with plain `div`s; the app has no chart library. One bar per day (per week over 90 days, counted from the oldest; per hour for Today), stacked, with no gap between parts and a 2 px radius on the whole bar's top corners, at most 28 px wide and 2 px apart. The 5 with the most cost get `--series-1` to `--series-5` and the rest share `--series-rest` (in `theme.css`, a light and a dark step each: the dataviz skill's categorical palette, blue, orange, aqua, violet, magenta, checked with its colour-blind and contrast checks on the dialog's colour in both themes; its yellow is left out because amber means waiting). The plot is 190 px high with a 44 px gutter: a hairline per `axis` step (0 up to the first 1, 2, 2.5 or 5 times a power of ten that reaches the biggest bar in 3 steps), its value in the gutter, and the top step is the top of the plot. Today's bar (or this hour's) is at 70% opacity: it isn't over yet. Dates under it: the first, the last and about one every 7 bars between (every bar with 10 or fewer; hours at 00, 06, 12 and 18). One pointer handler on the bars works out the slot from the pointer's x: the slot gets a `--hover` band and a box beside it (to its left in the right half; it never leaves the card or takes the pointer) with the date ("Mon Nov 16", "so far" for today), the total, and a line per series that cost something that day, most first. The plot is one `role="img"` whose label says the range, the total and the busiest day. Under it, the legend: a dot, the name (`accountName` or `modelName`) and that series' cost over the range. A range with no cost says "No cost in this range." in the plot's place.
- **Wording** (`lib/usage.ts`, unit tested): `tokens` (950, 1.2K, 3.4M, 31.5B), `money` ($0, <$0.01, $12.35, $12,346), `resetsIn` ("resets in 1 h 40 min", "resets in 3 d 2 h", "reset"), `high` (over 80), `modelName`, `projectParts`, `change` ("12% more", "20% less", "the same").

**Give a Secret…** (right-click a session that has a Claude `sessionId`): a dialog with Name (a text field; the server's saved names from `GET /secrets` as suggestions) and Value (a masked textarea, not a password field: a password field drops line breaks, which would break a PEM or SSH key; Enter sends, Shift+Enter starts a new line). Save and Tell Claude sends `PUT /secrets/<name>` with the value in the body, clears the field, then `POST /secrets/<name>/tell`; with a saved name and no value the button is Tell Claude and only tells. A name the server would refuse is caught first (`src/lib/secrets.ts`). An error stays in the dialog (Claude asking: the secret is saved, Tell Claude tries again). The value is never in a URL, localStorage, the terminal or a log. Settings > Models lists each server's secrets by name with Remove (`DELETE /secrets/<name>`); an older blimpd (404) shows none.

**Servers** (`components/ServerSwitcher.tsx`, `ManageServersDialog.tsx`, `AddServerDialog.tsx`, `lib/hints.ts`). A server is known everywhere by its key, `user@host:port`: the tunnel id, and the key of its recent folders, saved layouts and windows. A name (`Server.name`, set in Manage servers or when adding) is only what the app shows and is never part of the key. `serverName`: the name given, else the host; two saved servers that would read the same each show their key instead. The name is on the tab chip, Welcome, Open Folder, Settings, the update bars, the Home tab and its server list, and the Server menu; tooltips and Manage servers also show the key. With more than one server saved, ⌘K rows and the waiting and job notifications name the server. Every window keeps the list: a save sends `servers-changed`, and each window loads the list again, so a server added, renamed or removed in one window shows in the others.
- **Server list**: on the Home tab, the first in the top bar, also with one server (with so many tabs that the strip scrolls, Home and its chevron scroll with it; the Server menu still has the list). After the house, Home's server's connection dot, its name (cut with "…" when the tab is full) and a chevron button (accessible name "Servers"). A click on the tab goes Home as before; a click on the chevron opens a menu under the tab (the `.menu` recipe, fixed, outside the tab strip, which scrolls and would cut it off; Esc or a click outside closes it and gives the chevron back the focus): one row per saved server, in saved order, with its dot, its name and "N sessions", plus the amber dot and a count when sessions there wait for you; a server not connected says "offline" (in the danger color) or "connecting…" instead, with the error as the row's tooltip. Home's server has a ✓ and `aria-current`. A row shows that server at Home. Then Add server… and Manage servers…. So adding a server is never hidden behind an open file, as it was when Add server was only on Welcome. The chevron is a button of its own just after the tab element, styled as part of the tab, so it never selects, drags or closes the tab, and Home stays a tab with no button in it. It was a separate button before the tabs at first; it moved onto Home because both named the server and both wanted to be first.
- **Manage servers**: one block per saved server: Name (saved on Enter or on leaving the field; empty means the host), the address (the key, selectable), a state line ("connected · blimpd 0.3.15 · 4 sessions", or the whole error and its hint) and the buttons that apply: Try again (not connected), Install blimpd (the not-set-up error, Mac app only), Update server (blimpd older than the app; the update bar's own path, `updateLink`), and Remove…, which asks in place first ("Remove <name>? Its tabs close. Sessions on the server keep running."). Any server can be removed, connected or not. The footer has Add server…. Renaming changes no key, tunnel, tab or recent folder.
- **Add server**: Host (with the `Host` names of the Mac's `~/.ssh/config` as suggestions, `ssh_hosts`), User, Port and Name. The note says what Host takes: a name from the SSH config, a Tailscale name, or an address. The server is tried before it is saved (`tryConnect`: the same `connect` its link makes, so the tunnel that opens is the one the link reuses), with "Connecting to <host>…". On success it is saved, its Home opens and the dialog closes. On failure the dialog stays with the fields as typed, the error, its hint, and Try again, Install blimpd (only for the not-set-up error, only in the Mac app; it installs, then tries again) and Add anyway. Each try has a random token of its own, passed to `connect` as `attempt`; Cancel (and closing or reloading the window, on `pagehide`) sends `disconnect` with that token, so Rust ends that try before it opens a tunnel, also when the cancel gets there before the connect does, and never touches a tunnel by server id: Add server, Cancel, Add server again for the same host connects the second try, whatever the first one does. A tunnel that was already up when the cancel arrived (the connect had just ended) stays as the server's until blimp quits. While Install blimpd runs, Cancel stops waiting for it and puts the form back as it was before the click (in the dialog, Cancel closes the dialog as always); the install's ssh may go on in the background until it ends or times out (ServerAlive, about a minute). A key already saved says "This server is already in your list.". With no server saved, the same form fills the window (`.welcome form`).
- **Hints** (`connectHint`): one line under an error the Rust shell returns, saying what to do: blimpd not set up (Install blimpd puts it there); host key not known ("Connect once from Terminal first: ssh -p 2222 max@box", the real command for that server); permission denied (the server doesn't take this Mac's key); a name that doesn't resolve, a timeout or a refused connection (check the name, and that the server is on). Other errors get no hint. Add server, Manage servers and Welcome's offline box show it.

**Commands** (`lib/commands.ts`): one table of the app's commands, each with an id, its title (the menu's, in title case), the menu it belongs to and an optional key. It is plain data, so tests check it (ids unique, no two commands share a key, none takes a key the terminal keeps), and the menu bar and the Keyboard Shortcuts dialog are made from it, so neither can go stale. On each render App says what each command does in this window, whether it's on, and for the panels whether it's checked (`Action`); the front workbench adds Quick Open, Save and Close Tab, so those act only in the front tab. `server:<n>` (the n-th saved server's Home) and `recent:<n>` (the n-th recent folder of the front tab's server) are worked out from the id. One window key handler (capture phase, so it works with the terminal or an input focused; never with Control held, which is the terminal's; ⌘K inside Monaco is Monaco's) looks the key up and calls `run(id, "key")`; a menu click calls `run(id, "menu")`. A command that is off does nothing, as its key did before (⌘O with no server connected still says "No server is connected yet."). `run` drops a second run of the same id that comes from the other source within 250 ms. Why: on a Mac the page gets a ⌘ key first and the menu gets it only if the page didn't handle it, but that differs with focus and with the WebKit version, so one press can arrive from the page, from the menu, or from both, and it must act once.

**Shortcuts**: ⌘K jump palette: fuzzy over every session's title, folder and name across servers; Enter shows it in its folder's tab here if there is one, else brings forward another window with that folder in a tab (`focus_project`), else opens the folder in a new tab here. Ranking: a contiguous match beats a scattered one, a match at a word start beats one mid-word, and a title match beats a folder or name match. When focus is inside Monaco, ⌘K goes to Monaco (its ⌘K chords, as in VS Code), and so does the next key that isn't a modifier, also one that is an app command (⌘K ⌘0 folds all; it doesn't reset the text size). Only within 5 s of the ⌘K, and while the window keeps focus, as Monaco waits for it (`inChord`). ⌘N new Claude session here. ⌘⇧N new window. ⌘O Open Folder: recent folders (`/folders/recent`), browse (`/fs/list`, with New folder), or a typed path. ⌘P quick open. ⌘S save now. ⌘W close the active file tab (from anywhere in the window; nothing when no file is open). ⌘T new browser tab. ⌘B files. ⌘J terminal. ⌘⌥B session list. ⇧⌘W close the window (Rust does it, from the menu; nothing in a browser). ⇧⌘[ and ⇧⌘] the previous and next project tab, wrapping round (matched on `e.code`, as ⌘⌥B is: ⇧[ types "{"). ⌘= or ⌘+ (⇧ allowed), ⌘- and ⌘0: the terminal and editor text sizes both up or down by 1, within Settings' 9 to 28, or both back to the defaults. These three are matched on the character typed, as the Mac menu matches them, so they follow the keyboard layout; ⌘0 also on the 0 key itself (`Digit0`), for layouts where a digit needs ⇧. A window ignores its own `settings-changed` event (it carries the sender), which can arrive after a newer change made there. Keyboard Shortcuts (Help menu, or All shortcuts on Welcome): every command with a key, grouped by menu and made from the table, then the keys that are not commands (the files pane's, the terminal's, Esc). Esc closes dialogs (and cancels a session drag).

**Waiting**: when a session's state becomes `waiting` (not on first load), send a notification "<title> is waiting for you" (body: the folder; with more than one server saved, "<server name> · <folder>"), unless this window is focused and shows that session in a split of the tab in front. In the Mac app every window watches, and `claim_notice` lets exactly one notify (none if any focused window shows it). Dock badge = number of waiting sessions on connected servers (`getCurrentWindow().setBadgeCount(n || undefined)`), only in Tauri; it's app-wide, so every window sets the same number.

**Look**: native-feeling Mac app, not a web page. Dark by default (follows system light/dark), compact type (13 px UI, system font), subtle 1 px dividers, no heavy shadows or gradients. Accent for "waiting" only. Colors as CSS variables in one file. A server's connection state is a shape, not a new color: connected is a solid dot in `--fg-dim`, connecting a hollow ring, offline a solid dot in `--danger`. There is no green.

### Content security policy

The UI renders files from servers (Markdown, SVG, PDF, HTML), so script injection must be impossible and, if it ever happened, contained. The same policy is set in `app/src-tauri/tauri.conf.json` (`app.security.csp`) and as a `<meta http-equiv="Content-Security-Policy">` in `app/index.html`, so the e2e tests run under it too:

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' blob: data:; font-src 'self' data:; worker-src 'self' blob:; connect-src 'self' ipc: http://ipc.localhost http://127.0.0.1:* ws://127.0.0.1:*; frame-src http://127.0.0.1:*; object-src 'none'; base-uri 'none'; form-action 'none'
```

(Vite's dev server needs `ws://localhost:*` for hot reload; add it only in dev.) pdf.js (pdfjs-dist 6, which never uses eval) runs with scripting off. Tauri capabilities (for the web views `main` and `w-*`, by web view label) grant only what the UI uses: the app's own commands (`build.rs` lists them: tunnels and port forwards, windows, transfers, the menu), event listen, set-badge-count, set-title, the web view's size (to place a Finder drop: `dropPoint` in `lib/transfers.ts`), notification, store, opener limited to `http:`/`https:` URLs and reveal-in-Finder. The dialog plugin is used from Rust only. No shell, fs or http plugin. `frame-src` allows only `http://127.0.0.1:*`, for visuals: a visual's tab is a frame of blimpd's copy through the tunnel, sandboxed with `allow-scripts` only, so it runs as an origin of its own, and blimpd's own policy on the page allows no requests. A frame can't be sent to a website; it can be sent to any address on the Mac's `127.0.0.1` (any local service, not only blimp's forwards): a GET with no click, after which the frame shows that service's page under that page's own rules, still with no blimp token. The tunnel's port changes per server, so the fixed policy can't name it. Browser tabs are frames of the server's Chrome, drawn in a canvas. An HTML file's page is a `srcdoc` frame (no URL is loaded, so `frame-src` doesn't apply), sandboxed with no flags, and it keeps this policy.

### macOS menu

The page describes the menu bar and Rust draws it. The page knows what each command does now and whether it's on or checked (the command table and App's actions); Rust holds the only menu permission (the page has no `core:menu:*`), so what an item may hold stays small and checked in one place.

- **The description** (`menuSpec` in `src/lib/menu.ts`, pure and unit tested): plain JSON, a list of menus. An entry is a separator, a native item by name (about, hide, hide-others, show-all, quit, undo, redo, cut, copy, paste, select-all, minimize, zoom, fullscreen, bring-all-to-front: AppKit does these, and they never reach the page), a command (id, title, optional key, enabled, optional checked: then it's a check item) or a submenu. A submenu with `role` `window` or `help` gets Tauri's Window or Help menu id, so macOS lists the open windows in it and shows the Help search box. Keys are written as muda reads them, by physical key: `Cmd+Comma`, `Cmd+Shift+BracketLeft`, `Cmd+Equal`, `Cmd+Alt+KeyB`. Tauri offers only physical keys, so Bigger Text shows as ⌘= in the menu. Titles are cut to 200 characters and control characters become spaces (`fit`), since a server's name or a folder can be anything. Rust doubles each `&` when it draws a title (muda reads a lone `&` as a mnemonic mark and drops it), after checking the title as typed.
- **Sending it**: the menu is app-wide on macOS, so the focused window describes it. It sends `set_menu` when it gains focus, about 100 ms after a change while it has focus (App rendering, or the front workbench saying its Save and Close Tab changed: a file opened or closed, Quick Open shown or hidden, which App alone wouldn't see; a burst of changes is one call), only if the JSON differs from the last one sent, and again after each menu click (a check item ticks itself when clicked, which could leave it stale). Rust ignores a description from a window in the background unless it is the only window. The page calls `set_menu` only in the Mac app.
- **Checks in Rust** (`validate` in `src-tauri/src/menu.rs`, pure and unit tested): only menus at the top; ids `[a-z0-9:-]{1,64}`; titles of 1 to 200 characters with no control characters; at most 400 entries and 3 menus deep; an unknown field, kind or native name refuses the whole description. A key Rust doesn't take (it needs ⌘, allows ⇧ and ⌥, never Control, and a letter, a digit or a named punctuation key) only leaves that item without a key. On Linux `set_menu` only checks, since there is no menu bar.
- **Clicks**: one event, `menu`, with the item's id, to the focused (key) window; the page runs `run(id, "menu")`. Rust does two ids itself: `close-window` closes the focused window (a normal close, so the window bookkeeping forgets it as for the red button), and `new-window` opens a window when no window is focused (every one minimised, or none left; with a focused window, it goes to the page like any other id). With no focused window, only the app-wide items go to `main` (or, with `main` closed, any other window): `settings` and `check-updates` unminimise and focus it first, so the sheet or the update bar is seen; `help` and `report` only open their page. Every other click is dropped, rather than done in a window that can't be seen (`route`, unit tested). Open Recent's `recent:<n>` opens the n-th folder of the list the menu was last described with, and Forget on Home describes the menu again.
- **Built-in menu**: before any page has described the menu, and again when the last window closes, Rust shows a small one (`fallback`, checked by the same `validate`): blimp (About, Hide, Hide Others, Show All, Quit), File (New Window ⇧⌘N), Edit (the six native items), Window (Minimize, Zoom), Help.

The full menu (title case, as Mac menus are; inside the window the app keeps sentence case):
- **blimp**: About blimp · Check for Updates… · — · Settings… ⌘, · — · Hide blimp · Hide Others · Show All · — · Quit blimp
- **File**: New Claude Session ⌘N · New Shell · New Browser Tab ⌘T · New Window ⇧⌘N · — · Open Folder… ⌘O · Open Recent ▸ (the front server's recent folders, at most 10, with `~`; off when there are none) · Quick Open… ⌘P · — · Save ⌘S · — · Close Tab ⌘W · Close Project · Close Window ⇧⌘W
- **Edit**: Undo · Redo · — · Cut · Copy · Paste · Select All (native)
- **View**: Files ⌘B · Terminal ⌘J · Sessions ⌥⌘B · Browser Tabs (each checked while shown; Browser Tabs off while the folder has none) · — · Jump to Session… · — · Bigger Text ⌘= · Smaller Text ⌘- · Default Text Size ⌘0 · — · Enter Full Screen
- **Server**: each saved server by name, the front tab's server checked, a click going to its Home · — · Add Server… · Manage Servers… (off while no server is saved) · — · Reconnect · Update Server… (off unless the front server's blimpd is older than the app) · — · Usage… (off while the front server is not connected). No session counts and no connection state: they change all the time (a server that can't be reached goes between offline and connecting every few seconds), and each change would redraw the menu, which shuts a menu that's open. The top bar and the Home tab show the state. Nothing else in the description depends on offline versus connecting: Open Recent's items stay on while the front server reconnects, and say it isn't connected yet when clicked then.
- **Window**: Minimize ⌘M · Zoom · — · Show Previous Tab ⇧⌘[ · Show Next Tab ⇧⌘] · Go to Home · — · Bring All to Front, then the windows macOS lists
- **Help**: Keyboard Shortcuts · blimp Help (the README on GitHub) · Report a Problem… (a new GitHub issue)

Jump to Session… has no key in the menu: a menu key wins over the page, and inside the editor ⌘K must reach Monaco, where it starts its chords. So ⌘K stays a page key only (`pageOnly` in the table). Every other key is both in the menu and handled by the page; `run`'s 250 ms rule makes one press act once either way. There is still no Print ⌘P.

## Brand

The mark is a refined blimp facing right: a shaded white envelope with two panel seams and a highlight, four fins at the tail, and a gondola with three windows (design in `docs/superpowers/specs/2026-10-25-brand-refresh-design.md`). Its sources are `brand/blimp-silver.svg` (for dark backgrounds) and `brand/blimp-ink.svg` (graphite, for light ones); the iPhone's asset catalog (`BlimpGlyph`, ink in light mode and silver in dark; `BlimpGlyphOnDark`) and the Mac (`app/src/assets/`) ship copies, which `test/brand.test.ts` keeps the same. The icons are the mark on graphite (`#2b2c33` → `#0c0c0f`): `ios/app-icon.svg` and `app/src-tauri/app-icon.svg`, rendered by `bun scripts/icons.ts`.

The name is written in the system's rounded font, heavy. Buttons are monochrome: black, white in dark mode, on the iPhone (its root tint), `var(--fg)` on `var(--bg)` on the Mac, following its theme. The Mac shows the silver blimp in its dark theme and the ink one in its light theme. Colour means something: amber for needs you, blue for unread and for links, and the swipe actions' red, green, blue and grey. The Usage window's bars are the one place colours stand for names, with the matching dots in its legend, hover box and table, and a legend says which. The blimp appears on the pair screen, the lock cover, an empty inbox and beside "Connecting…" on the iPhone, and on the Mac's welcome page and connecting pill; it drifts or bobs, and keeps still with reduced motion.
